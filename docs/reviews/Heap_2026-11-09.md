# Heap — 2026-11-09

Drafted for the maintainer, at their request (2026-11-09): our options
and intentions for the heap, reviewed toward a high level of
parallelism; where the current plans hinder parallelism and the
integration of the parts into one evaluator; and alternatives
brainstormed free of the Rust bootstrap and of the current sketch. Two
reviewers read the same sources: the agent, and a Fable sub-agent
working independently, whose findings are marked as its own and were
checked against their sources before they were reported. This review
proposes; the maintainer decides. It creates no plan, no step and no
record.

## The question

The maintainer (2026-11-09): "Until recently, I've been viewing our heap
of cells as a global resource outside our nets." Parallel computations
would each hold a slice of the net and authority over some cells, but
"heap contention is realized as halting early to query or update a heap
state. If we aren't careful in our design, fine-grained interrupts will
break Bend's parallelism." The alternative: "hierarchical, fractal
structure. Each net has a heap", so that what a net allocates and never
shares makes no contention, linear objects migrate without a trace, and
shared ones are tracked. Further, nets *as* heaps: lists, dicts, perhaps
bignums as net structures, specialized node kinds, reference-counted
data nodes as allocations within a net, and "a node that captures
lowered data into a `Data(Net)` node".

## What Bend allows

- **Parallelism is balanced fork-join, and nothing else in pure code.**
  "Bend's current scheduler is a contention-free, binary fork-join
  machine: every task is handed to a core exactly once and never moved
  afterwards", so "you must keep the workload balanced" (`bend guide`,
  Parallelism). `IO.fork` interleaves computations on one event loop;
  only parallel calls run pure code in parallel.
- **A round costs barriers.** About 7.6 µs on 2 threads, 11 µs on 4,
  19 µs on 8; "Rounds want a few hundred microseconds of work per worker
  to keep that under 5%; a request waits up to a round"
  (`Architecture_2026-10-26.md:289-296`).
- **Sharing is immutable and counted.** One heap, no collector, values
  affine and copies counted, and "a `+` value read by every lane costs
  an atomic per read" (`bend guide`); a count saturates at 2^24, a
  fail-stop (`intern-hot-values`).
  Arrays are affine: "Closures and arrays are affine (`Type`), so they
  cannot sit inside shared data" (`Architecture_2026-10-26.md`, Values
  and large structures). Atomics and forked arrays exist only under
  `@unsafe`, outside the proofs (`split-heap`).

The consequence that frames every option: **in Bend a value can be
shared or evaluated in place, never both.** Bend data is immutable and
shared; a live net is affine and owned. A lazy value that two tasks need
has one owner, and the other task waits for it or computes its own copy.
The global store makes the owner whoever holds the cell's page this
round; heaps per net make it the heap that made the value. No design
removes the owner; a design chooses where it is and how rarely others
must ask it.

## Intentions

What the docs ask of the heap, and whether each is semantics or cost:

| Intention | Where | Kind |
|---|---|---|
| Results never depend on scheduling | `diagnostic-order-follows-schedule` | semantics; purity gives it under any schedule |
| Non-strictness: what nothing demands fails nothing | `net-demand-whnf`, `net-error-values` | semantics |
| "a thunk forced twice computes once" | `HeapModel_2026-10-27.md:19` | cost; a duplicate evaluation of a pure value is unobservable |
| Copies of a function share its source's reductions | `functions-are-nets-with-arity` | cost; met by reducing once before copying (`copy-reduced-function-nets`) |
| Laws over the core; no `@unsafe` in it | `split-heap` | engineering choice, held so far |
| Reclamation of what is unreachable | `store-collection` | cost; a batch assembly may run without it for a long while |
| "eventually a high level of parallelism" | the maintainer | goal |
| Kernel data types adopted into the final evaluator | `lambdas-lower-to-nets` | engineering goal |

The test behind the last column is the design's own: "Assembly-time
performance never affects results, only speed" (`docs/DistilledDesign.md`,
Performance), so a requirement is semantics only if relaxing it could
change `asm.result`. Restating "computes once" as a cost bound matters
most: a bounded duplicate of a cheap value can replace a wait, while a
lost sharing of an expensive one can be exponential. The bound wanted is
no asymptotic loss of sharing, not "never twice". Duplication has one
precondition, which the second reviewer found: no step may mint an
identity by count (below).

## Findings

**F1. The global store makes every shared lazy value a point of
contention.** `split-heap`: everything not ground "has identity in our
own store"; `store-pages`: "A handle names a cell as one `U32`: the page
number in its high bits, the slot within the page in its low bits";
`rounds-of-coarse-work`: "A worker that finds a task needs a thunk it
cannot proceed past records the requirement and goes on with its other
work." A handle means something only to the holder of its page, so a
task meeting one it does not hold stops, and its request waits up to a
round. The cost is on record: "the Rust bootstrap's largest evaluation
cost was one coordinator round trip per lazy value, about 60 per level of
recursion" (`HeapModel_2026-10-27.md:123-125`). Blocking for high
parallelism; the maintainer's heap per net answers it.

**F2. Cells never move, so locality cannot follow the work.**
`store-pages`: "Cells never move, so handles stay valid." A task's
working set ends up spread over pages others allocated, and a linear
object cannot migrate with its user. Big pages already turned parallel
runs memory-bound (`Architecture_2026-10-26.md`, the table under Pages
and rounds). Costly.

**F3. One coordinator and one collector, by design.**
`rounds-of-coarse-work`: "A coordinator in the pure core runs evaluation
as rounds: it splits work into tasks, learns from each task which pages
and thunks it needs next"; `store-collection`: "Collection runs in rounds
by pages, as evaluation does; marks crossing pages travel between
rounds." Every request resolves at the center and every round is a
global barrier. EvalSpike already saw the alternative:
"Deep parallelism may simplify the coordinator by making it recursive: a
worker coordinates subtasks over the pages it holds"
(`spike-deep-parallelism`). Under heaps per net, coordination is
recursive and most garbage dies with its net. Costly.

**F4. "A function's net is shared, mutable" no longer holds, and it
still sizes the store.** `functions-are-nets-with-arity`, Consequences:
"A function's net is shared, mutable and must be reclaimed, like a lazy
value: both need the shared store"; `Architecture_2026-10-26.md:92`:
"Its net is therefore shared and mutable, like a lazy value, and lives
in the store beside them." Since `copy-reduced-function-nets` (reduce
locally, then copy whole) and the maintainer's answer to the cells
review (evaluate the function's net eagerly before freezing), a frozen
function is an immutable template: Bend data, shared without
contention, its copies independent. Only thunks, promises and knots
need an owner. Minor in itself; it shrinks the problem.

**F5. The Cells plan inherits the global namespace.**
`Cells_2026-11-09.md`, The model proposed: "Each top-level definition is
a cell, named by a `U32` handle assigned before any definition is
lowered", forced on one stack. A value holding such a handle cannot leave
the evaluation without the store. And within one net the plan adds less
than it seems: the static linking built at `ladder-thunks.globals`
already evaluates each definition once per net, shared by fans; what a
net lacks is recursion, knots, and sharing with other nets. Costly if
kept; cheap to change now.

**F6. Laziness inside data ties data to the store.** `split-heap`:
"Structures holding handles have two representations, inline and in the
store; rope and dict code handles both"; the sketch's `Val` holds
`Lazy{cell: U32}` and `Fun{net: U32, +arity: U32}`
(`Architecture_2026-10-26.md`, Values and large structures); the Cells
plan's item 8 is open. A dict of lazy members carries handles, so it
cannot move between heaps without its cells. Which representation
partial data takes decides what "the kernel's data types adopted into the
final evaluator" means. Costly; the central integration question.

**F7. Demand leaves no parallel work inside a net, and the plans name no
non-speculative source of parallel demand.** `net-demand-whnf`: a forced
net "reduces only the pairs that lie on the way"; `net-nodes-double`:
"parallelism inside a net comes from accelerated operations, not from
spreading the net across workers"; `rounds-of-coarse-work`: "Programs
must expose concurrent tasks (sparks, reflection tasks, independent
work) for rounds to pay off." Missing from every list: strict bulk
consumers. Serializing `asm.result`'s bytes needs every section; an
append needs its operands' spines; a hash, a comparison, a length need
the whole. Such an operator may demand its parts in parallel with no
speculation at all. For an assembler, whose output is demanded whole,
this is likely the largest source. A gap rather than a hindrance.

**F8. Read-mostly sharing across lanes is counted only for hot values.**
"a `+` value read by every lane costs an atomic per read" (`bend guide`);
the sketch answers with interning, for the 24-bit bound
(`intern-hot-values`). Templates, namespaces and constant tables will be
read by every worker all the time; whether each read pays an atomic, and
whether a per-worker replica is cheaper, is unmeasured. Costly until
measured.

**F9. The heap's design is spread over five plans, all assuming the
global store.** Architecture's "The store" and "Pages and rounds",
HeapModel's cells and workers, NetData's `netdata-lazies` ("a reference
to another cell's value") and `netdata-borrow`, EvalSpike's
`spike-page-rounds` and `spike-fixpoints`, and the Cells plan each carry
part of it. A ruling on heaps per net changes all five at once, and no
one of them owns the question. Minor in cost, but it is how a
superseded assumption survives.

**F10. What goes well: the kernel is already per net.** `net-nodes-double`:
"Node references are indices local to their net; heap handles are
`store-pages`'." The kernel, its laws and the lowering never need a
global address; only the handles inside data do. Heaps per net change
the layer above the kernel, not the kernel. Final data as Bend data is
parallel already: "a parallel fold over a persistent tree ran 5.7×
faster on 8 threads than on 1" (`Architecture_2026-10-26.md:107-108`).
Levels make a copy position-independent once offset, which is what moving
a net between heaps needs.

## The maintainer's ideas

**Heaps per net, as an affine tree.** Each heap owns its net, its table,
its own cells and its child heaps; a child is handed to a parallel call
and returned at the join. What a heap allocates and never exports costs
no one else anything, and dies with it. A linear result moves into its
parent whole: moving an affine array costs nothing in Bend. What it
costs:
- *Closing a boundary.* A child's subnet with wires into a subnet the
  parent shares (a fan on the boundary) is not closed. Each crossing wire
  is resolved before the child runs: the shared subnet promoted to a cell
  the parent exports, copied, or forced first. In a leveled net the
  crossing wires of a box are exactly those carrying its controls, so the
  boundary is known.
- *Entanglement.* Nested parallelism free of determinacy races is
  disentangled: concurrent tasks never learn of each other's
  allocations, so each task's heap can be managed on its own (Westrick,
  Yadav, Fluet and Acar, "Disentanglement in Nested-Parallel Programs",
  POPL 2020, the basis of MaPLe's heaps). Laziness is mutation, a thunk
  written when forced: a sibling that writes its own result into an
  ancestor's thunk, which another sibling then reads, entangles them. The
  answer is a policy (wait, duplicate, or take the thunk over), not a
  lock.
- *Tracking shared objects.* An exported cell outlives the child that
  made it; at the join, the parent adopts the child's exports and the
  handles to them are rebased, or kept stable by a forwarding table.
- *Balance.* Heaps do unequal work; the scheduler cannot move tasks. Fuel
  quanta per round bound the imbalance (a round runs each child at most
  so many steps), and balanced data structures give balanced forks.

**Nets as heaps.** Partial structures as net structures buy laziness and
knots inside data for free: a lazy member is a subnet, shared by fans,
evaluated once within its net, and the Cells plan's item 8 dissolves
inside a net. They cost an interaction per constructor per traversal
where Bend data costs nanoseconds per element, interactions for every
key search, and sequential bulk work under demand. Church, Scott and
Mogensen-Scott encodings are uniform and slow; node kinds of our own
(a cons, a dict node holding its key, number limbs) are faster, and the
kernel has precedent in its operator nodes (`operator-nodes`). A
constructor holding lazy fields is a box per field when fans copy it,
which NetPairing has not covered. Reference-counted data nodes are what
the table already is: Bend data, counted by Bend; Bend's affinity makes
reuse in place natural when a count is one. Bignums gain least: their
arithmetic is eager and digit-serial, an interaction per limb against a
machine operation per limb in Bend data, so a net structure pays only
where digits are wanted lazily, as in exact real arithmetic; an
assembler's numbers are mostly small, immediates in the reference word
(`netdata-refs`).

**A `Data(Net)` node.** In Bend, data is immutable, so a captured net as
data is a template: copied wherever it is used, its evaluation never
shared. Shared evaluation needs an owner: a cell, a child heap. So
capture has two outcomes, a template (as a function is) or an owned heap
(a spark, a promise). Either way the subnet must be closed first (above),
and its levels set to zero, to be offset where it lands (the Cells plan's
item 2). It is the primitive that both sparks and lazy members leaving a
net need.

## Alternatives

Each with the experiment that would decide it.

- **A1. Rounds by fuel over a tree of heaps.** A round walks the tree's
  runnable heaps as balanced parallel calls, each running at most a
  quantum of steps; a request goes up one level, not to a center.
  *Experiment:* utilization against the quantum and the barrier cost,
  on heaps of uneven work.
- **A2. Duplicate rather than wait.** A task needing an unevaluated
  ancestor's value computes its own copy when the value is cheap, judged
  by its template's size or a recorded cost; at the join the parent keeps
  one result, equal by purity. Expensive values are waited for. GHC's
  parallel runtime chose the same: "Because a thunk always represents a
  pure expression, semantically it doesn't matter if two threads
  evaluate the same thunk"; cheap thunks go unlocked, "we are prepared to
  risk duplicating their work", and "for expensive thunks the overheads
  of locking are quite acceptable" (Harris, Marlow and Peyton Jones,
  "Haskell on a Shared-Memory Multiprocessor", Haskell Workshop 2005,
  sections 3.2 and 4). *Experiment:* duplicates and their cost on
  workloads sharing definitions.
- **A3. Strict bulk consumers fork their demand.** Serialize, append,
  hash, compare and length demand their parts in parallel over balanced
  structures. *Experiment:* the output path of an assembly with many
  sections.
- **A4. Templates for code, cells only across heaps.** Within a net,
  definitions stay linked statically and shared by fans; recursion is a
  reference to a template, spliced where demand meets it, as HVM2's
  references to closed top-level nets are expanded where they interact
  (its paper's REF nodes, which it credits with some laziness in a
  strict runtime); a knot is a cell local to its net.
  Cells with handles exist only for values that cross heaps.
  *Experiment:* the Cells plan's recursion sample through template
  references, against cells.
- **A5. Partial data in nets, final data as Bend data.** A structure is a
  net while any part is lazy, and is grounded into a rope or a dict once
  complete, where bulk work forks in balance: `split-heap`'s grounding,
  moved inside the net. *Experiment:* a list built and consumed as net
  structure against a rope, at n, 2n and 4n elements.
- **A6. Exports with stable names.** A heap exports a shared cell under
  a name of its own; at a join, the parent adopts its child's exports and
  a table rebases the names. *Experiment:* the rebasing cost per join.
- **A7. Snapshot reads.** At each round, workers get the evaluated cells
  as one persistent map, shared in O(1) as Bend data; they read without
  stopping and return what they computed, merged at the barrier.
  *Experiment:* the cost of lanes reading shared data (F8).
- **A8. Parallel tasks from the definitions' graph.** The front end knows
  which definitions refer to which, so independent parts of `asm.result`'s
  demand can be tasks from the start, speculative only where demand is
  conditional.
- **A9. One rule for what crosses a heap.** A value leaving its heap is
  final data, a template, or an exported handle, never a handle local to
  a net; a type of its own makes the wrong one unrepresentable, as
  HeapModel's cached copies are (`HeapModel_2026-10-27.md:135-145`).

## The second reviewer

Fable read the same sources and wrote its review on its own, kept as
written in [`HeapFable_2026-11-09.md`](HeapFable_2026-11-09.md). Its
quotes were checked against the repository and hold. It agrees on the
framing: call-by-need sharing is a cost goal, the live net is the
natural unit of exclusive ownership, cells are needed only where values
cross nets, function nets are immutable templates once frozen, and
lanes reading shared data need a measurement. What it adds, in its own
numbering:

- **H1, blocking: a busy cell is not a cycle once there are tasks.** The
  Cells plan's item 6 makes "A need on a busy cell" a strict cycle.
  Under rounds, busy also means held by another worker this round, so
  the rule would cache a false cycle as an error, depending on the
  schedule: a leak into results. HeapModel had the right method from the
  Rust bootstrap: "cycles are found by walking blocked producers' single
  dependencies, and all members fail together" (Comparison). A busy cell
  carries its owner, and a cycle is a need on an ancestor in the
  waits-for graph; one stack is the case where that graph is a path.
  Fixed in the Cells plan with this review.
- **A1: the exclusive resource is a live net, never a page.** Recipes and
  values are immutable Bend data and may go to any worker; only a live
  net is held by one. Today even a read of a finished value waits a
  round when its page is held elsewhere: "A value already forced needs no
  page: the coordinator shares it out between rounds"
  (`Architecture_2026-10-26.md`, Pages and rounds). Two workers may
  force one recipe and the first result is kept. This keeps
  `store-pages`' handles and changes only what is owned: a smaller step
  than heaps per net, answering F1 and F2 for reads.
- **Duplication's precondition.** A second evaluation is harmless only
  if no step mints an identity by count. `anno 'scope_unique` "wraps a
  given atom with unique metadata. If ever we compare the same atom with
  different metadata, we diverge instead" (`docs/Syntax.md`, Atoms), and
  objects made at run time ask the core for fresh cells (Cells plan,
  item 7). Both must derive what they mint from the forcing cell's handle
  and the ordinal of the mint, never from a counter, so that two
  evaluations mint the same identities.
- **A4: the need rate first.** Cross-cell needs per thousand
  interactions, and the depth of need chains, on the ladder under cells:
  high, and no ownership scheme saves the rounds, so cells must be fewer
  and coarser; low, and pages were never needed. `cells-data` yields it
  nearly free.
- **A3: close boxes in the front end.** Full laziness and lambda lifting
  float closed expressions out, emitted as templates at compile time; a
  box still capturing locals is cut at its free wires into cells, as the
  STG machine makes every captured thing a heap object. A census of the
  ladder's lowered nets, boxes by number of free wires, says how much
  this buys before any mechanism is built.
- **A5: frozen templates as cache keys.** A frozen net is canonical data,
  so its hash can address persistent caching (DistilledDesign,
  Performance); a live net never can.
- **Smaller points.** H4: the protocol's state should already be a task,
  the single stack its first container. H7: marks crossing pages travel
  as messages, a round a hop (`Architecture_2026-10-26.md`, Collection),
  which a heap per net mostly removes. H10: slices of 1 to 3 ms hold only
  a handful of rounds. H11: `net-capacity` says a large computation
  "spans nets and cells", but nothing splits a growing net yet.

Where the reviewers differ:

- **Global handles.** Fable keeps the global handle space for shared
  cells, objects above all: "the current global `U32` handle space is
  right for them and should stay". The agent proposed handles local to a
  heap, exported by name and rebased at joins (A6, A9). Fable's is the
  smaller change; the agent's removes the store's center, at the price of
  rebasing.
- **Dicts as nodes.** Fable doubts them, "since a dict's value is mostly
  looked up by key, a native tree's strength"; the agent left them open.
- **Demand.** Fable reads `net-demand-whnf` as no hindrance, other
  tasks' demands being other paths; the agent agrees, and adds strict
  bulk consumers as the source of parallel demand that needs no
  speculation (F7).

Fable's A1 and the agent's A7 combine: each round, every worker gets the
store's recipes and values as one persistent map, shared in O(1); only
live nets are dealt to one worker; a need on a busy cell waits or
duplicates.

## Recommendations

1. **Measure the need rate first** (Fable's A4): it says how much any
   ownership scheme can matter.
2. **Fix the cycle rule** (Fable's H1): done in the Cells plan with this
   review.
3. **Make the live net the one exclusive resource:** templates,
   recipes, values and final data are Bend data any worker may hold,
   dealt each round as one snapshot (Fable's A1, A7); a need on a busy
   cell waits or duplicates. This revises `rounds-of-coarse-work` and
   `split-heap`'s partitioning, which is the maintainer's to rule.
   Whether handles stay global or become local to heaps follows the
   measurements.
4. **Restate "computes once" as a cost bound,** with duplication's
   precondition on minted identities: a record, the maintainer's.
5. **Re-scope the Cells plan** before `cells-data`: definitions keep
   static linking within a net; recursion through template references;
   knots as cells; the protocol's state a task, the single stack its
   first container.
6. **Then measure:** the census of closed boxes (Fable's A3); net
   structures against ropes (A5); lanes reading shared data (F8); rounds
   by fuel over cells, on a chain and on a tree (A1).
7. **Give the heap one plan** once the maintainer rules: a successor
   takes the open heap steps of the five plans (F9), and they point to
   it.
8. **Keep open:** segmented heaps (a heap as several arrays, merged
   without copying), reduction of one net in parallel, cursors,
   collection.

## The maintainer's answers (2026-11-09)

- **"Computes once" as a cost bound,** read as "a small, local lazy
  computation could be duplicated. That would be acceptable." Two
  things to attend: `anno refl:(...)` "must emit a reflection task at
  most once (even if the task is cheap)", and in `(expensive + 42)` "we
  want to ensure `expensive` is not duplicated for work sharing".
  Recorded as `bounded-duplication`.
- **Partial data in the net, final data as Bend data** is "a valid
  option. I won't say 'should' here." What a value becomes may depend
  on whether it is duplicated, not only on whether it is final: final
  data used linearly may be more convenient and efficient kept as a
  net, with no translation, and leveraging that "may require flagging
  duplication".
- **The grain of parallel work:** "reflection tasks, separation of
  IDE/logger and assembly, Haskell-style sparks. Sparks would include
  map-reduce." There is "no direct alignment with Bend's parallelism,
  so keeping parallel operations near-equal will rely on heuristics
  around fuel and modeling our own scheduler."
- **Global handles** are one of the big questions, not answerable
  without hindsight. On consistency: "if we go hierarchical, then
  conceptually there is no clear 'global', just a node in a tree that we
  locally view as root. I wonder if modeling the toplevel as a net would
  simplify integration in some way." And "the question is ultimately
  how we reference things, and I don't see any fundamental need for a
  global identity over computations."
- **Measuring first** is usually good, "but we haven't actually
  implemented enough to measure, nor do we have representative examples
  to measure against. Not sure how to best approach this."
- **A representative assembly,** asked in reply: "The `hello world`
  direct-style assembly is perhaps the closest, though even that's
  pretty far from where I imagine ending up with glam long term.
  Something with plenty of backtracking conditionals, state, and at
  least some use of reflection tasks (or a viable placeholder for
  them)." The first is the ladder's capstone, `ladder-executable`; the
  second is now `ladder-measure.workload`, tentative.

## What the answers change

The agent's reading, for discussion; nothing here is a ruling.

- **Measuring with little built: model the scheduler by building it.**
  A coordinator in Bend over an abstract task, anything that takes fuel
  and returns its progress, its needs and its outcome, runs generated
  task graphs now and real nets later, paying Bend's real barrier costs
  either way. Generated families of glam programs at n, 2n and 4n, sizes
  from the command line, stand in for real assemblies: definitions in
  chains and trees, mixin chains, outputs of many sections, map-reduce
  over lists. They find superlinear growth, not typical costs. Counters
  go in as the ladder grows (needs, splices, freezes, fans meeting
  structures, emissions), into the results store. And the choices that
  are costly to reverse come last: a handle with global meaning inside
  `Val`, pages as the unit of ownership, a protocol whose state is not
  a task. Building `cells-data` with its cells belonging to the root
  heap and named relative to it costs what the plan costs now and keeps
  the tree open. The coordinator over abstract tasks is
  `spike-page-rounds.tasks`, tentative.
- **The representative workload is the scheduler's requirements.** Each
  feature the maintainer named asks something the plans mention only in
  passing. Ordered choice run ahead of need is speculation with a
  priority, the leftmost alternative first, and a cut cancels the
  speculative siblings: HeapModel already lists "abandonment of work
  after a cut" as missing. State under backtracking gives each branch its
  own copy, cheap only because Bend data is persistent. And a reflection
  task inside a speculative branch must not surface until the branch
  commits: emissions are buffered until then, a stronger rule than
  `bounded-duplication`'s "at most once".
- **Duplication, bounded two ways.** Statically, the front end flags a
  template holding `anno refl` or `anno 'scope_unique`, or work it
  cannot bound (a call it cannot see through, a recursion); only
  unflagged work is duplicated. At run time, a lazy value still being
  evaluated after one fuel quantum is claimed by its worker, and the
  others wait, so a duplicate costs at most a quantum. GHC's paper
  claims a thunk only when it scans the evaluating thread's stack, and
  names scanning "when the thread is descheduled" as "one plausible
  possibility" (section 4.6).
- **The copy fan as the duplication flag.** In a net a value is copied
  exactly where a copy fan meets it, and a linear value never meets
  one. So a final structure may stay a net while it is used linearly,
  and be frozen into Bend data where a fan first meets it, copied in
  O(1) after. Knowing a structure final takes a walk; where the walk
  finds a lazy part, copying falls back to fans, lazily, as now.
  Statically, the lowering's trie of uses already tells which locals
  are linear.
- **Fuel makes parallel calls equal by construction:** each worker runs
  its queue until it has spent one quantum, moving on whenever a task
  waits. The calls stay equal while each worker has enough runnable
  work, so the scheduler's job is slack, and tasks movable between
  rounds. Map-reduce over final data aligns with Bend's fork-join
  directly, over balanced trees. The IDE and logger as `IO.fork`
  computations interleave with the assembly on Bend's event loop "one at
  a time" (`bend guide`), each using parallel calls within its slices:
  responsiveness, not parallel speed.
- **Code global, computations relative.** Templates are immutable,
  closed code: shared everywhere, perhaps named by their hash (the
  second reviewer's A5), with no identity over computations. Only
  computations, cells and live nets, need names, and those can be
  relative to the heap holding them. A reference across heaps then
  behaves as levels do: an offset up the tree and an index there,
  adjusted as a value moves up, as a splice offsets levels. The
  toplevel as a net generalizes what runs today: the static linker
  already builds `asm.result`'s group as one net. The root heap would be
  the module's net, its definitions templates expanded on demand, its
  knots local cells, the shell talking to its interface.
