# Joins — 2026-11-11

How a live template's copy joins its cursors when a later
materialization reaches them: the design drafted for the Cells plan's
`cells-freeze.cursors.kinds`, with the agent's analysis, reviewed with a
Fable sub-agent, whose review is kept as written in
[`JoinsFable_2026-11-11.md`](JoinsFable_2026-11-11.md). The context is
`copy-reduced-function-nets` (live templates),
[`Cursors_2026-11-10.md`](Cursors_2026-11-10.md),
[`Positions_2026-11-11.md`](Positions_2026-11-11.md) and the Cells plan's
`cells-freeze` steps. This review proposes; the maintainer decides.

## The maintainer's question and remarks (2026-11-11)

The question: "Assume we have a net that's currently making a couple
copies of the same source, with positive and negative cursors into each
copy. We follow the negative cursor into the source, we do some
evaluation, then we materialize a couple nodes and some wires to the
positive cursors. How do we find the correct positive cursor to wire
against?"

On the answer below: "I also was thinking we might need some data
structure within our host net per active copy. That would either be a
side table or allocating some shared structures within the current
node heap. Whether a linked list is the best data structure is a
question to review after we have something working."

On uniqueness: "I think we can guarantee there are no extra join sites
per ring: a finished node will be copied linearly, at most once into the
host, and each port is a separate source position."

## The design

**The setting.**
- Source `S`, a live net.
- Copies `C1` and `C2` in host net `H`, made at level offsets `k1` and
  `k2`.

`C1`'s negative cursor at position `P` (a finished source node and one
of its ports) is demanded. `S` reduces the region behind `P` until a
value faces `P`, and the newly finished nodes are materialized into
`C1`. Each wire leaving them ends in one of three ways:
1. **at another new node:** the two copies are linked;
2. **at something still pending in `S`:** a new cursor in `C1`, negative
   or positive by the port's polarity;
3. **at a source port where `C1` holds an outstanding cursor:** a join.
   The new node's port is linked to whatever faces the cursor, and the
   cursor is freed.

**Two rules that keep each cursor unique.**
- **A copy fan waits at a negative cursor instead of duplicating it.**
  Demand through the fan's input meets the cursor as a need, it is
  materialized once, and the fan then copies the result by the ordinary
  rules. A duplicated cursor would join twice at one positive cursor.
- **A positive cursor never interacts,** not even with a merge facing
  it, as when the copy was itself copied by a fan. A join links the new
  node to whatever faces the cursor, so the levels' pairing is left as
  it would have been.

**Uniqueness and completeness.** By the maintainer's argument, a copy
copies each source node at most once, and each port is its own
position, so a copy holds at most one cursor per position. The same
fact gives completeness. When a node is copied, each of its ports whose
peer is not copied gets a cursor then, so a later wire reaching that
port finds the cursor.

**Joins at negative cursors too.** A materialization may reach a node
that became finished under another position `P′` of the same copy, still
outstanding. Its wire then ends at `C1`'s negative cursor at `P′`. So a
lookup searches all of a copy's outstanding cursors, not only the
positive ones.

**A structure for each copy in the host net.** The agent's draft is a
ring of nodes:

```
 C1:  [head: S, k1] → [neg P] → [pos q] → [neg P″] → back to head
 C2:  [head: S, k2] → [neg P] → [pos q] → …       (a ring of its own)
```

- **The head:** the source's handle in word 2, the offset in the
  header's field, and the next node of the ring in word 3.
- **A cursor:** its source position in word 2, and the next node of the
  ring in word 3. Its one port is wired into the copy.
- **Serving a negative cursor:**
  1. walk the ring to the head, for the source and the offset;
  2. run positioned demand in the source from the position;
  3. materialize at the offset. For each wire leaving the new nodes,
     search this ring for the far end's position: found, join and
     unlink; not found, insert a new cursor.

  The served cursor is replaced and unlinked.
- **Erasure:** an eraser meeting a cursor makes it a dead cursor, as
  the kernel's dead kinds are made today. The next search unlinks it,
  knowing its predecessor.
- **Lifetime:** reach and sweep follow ring words of cursor kinds, so a
  head lives exactly as long as some cursor of its copy does.

The maintainer leaves the structure open: a side table, or shared
structures in the host's heap; whether a list is best is to be reviewed
once something works.

**The alternative:** a record for each copy in the core, an array entry
holding the source, the offset and a list from positions to cursors,
with each cursor holding the copy's id and its position. Lookups are
quicker. But the core sees none of the kernel's erasures, so records
could only be freed when their host net ends.

## Dense position ids, explained

The second reviewer's idea 3 (`CursorsFable_2026-11-10.md`) replaces the
search by an index.
- **The ids.** The source gives each frontier position a small dense id
  (0, 1, 2, ...) when it first becomes a cursor position. It keeps the
  map from position to id, as a hash in the source or as a passive
  boundary node on the frontier wire holding the id.
- **The joins.** A cursor carries its source, its id and the offset, and
  each copy's join table is an array indexed by id. A join is one array
  read: no search and no hash. Ids are assigned once for every copy.
- **Fragments.** The finished part can be cached as a template whose
  ports are numbered, so a second copy splices the fragment instead of
  walking the source.
- **The costs:**
  - memory in the source: the map, or boundary nodes, which the
    maintainer finds awkward;
  - an array for each copy sized by the ids assigned so far, sparse
    where a copy reaches few of them;
  - fragments superseded as the source reduces further.

In this design, ids would turn each copy's ring into an array indexed
by id: the maintainer's "side table".

## The agent's analysis

**What the materializer does when it meets a finished node of another
tree.** A newly finished node `X` may hang under another outstanding
position `P′` of the copy, rather than under `P`. A wire from `P`'s tree
then reaches `X` by an auxiliary port, and that end gets a cursor keyed
by `P`'s side. When `P′` is materialized later, its wire reaches that
cursor and joins.

If the cursor is negative and is demanded first, positioned demand from
it meets a finished node at once. Serving it then means climbing `X`'s
principal links to the root of its tree, `P′`, a cursor of the same
copy, and materializing that tree. The cursor demanded joins on the
way. This must be part of positioned demand's frontier.

**Freezing a host that holds cursors.** A host `H` that is frozen in
turn, its value leaving its net or becoming a source, holds cursor nodes
in what it would copy. A cursor's principal faces an auxiliary port of
a finished node, so by the finished test it is finished. Copied as it
stands, a negative cursor would point straight into `S` and skip `H`.
That is the deep cursor the maintainer wants chained, since more work
may be shared through the intermediate net. So freezing must treat
cursor nodes as unfinished: a copy of `H` gets cursors into `H` at
them. Heads are reached by ring words only, never by ports, and are not
copied. To check with `glam/test_freeze.bend` once the kinds exist.

**Controls meeting a negative cursor.** The draft made a control meeting
a negative cursor a need. The maintainer (2026-11-11): "Level control
meeting negative cursor counting as a need is a bit awkward, TBH." Two
better forms:
- **No rules at all.** By polarity, only a node with a negative
  principal can face a negative cursor: an application, an operator, a
  copy fan, a Lift, an eraser, the interface. A negative cursor then
  needs no rule with any of them. It is served when demand's walk meets
  it, whatever faces it, as a handle is today. A pair off demand's path
  is never reduced (`net-demand-whnf`), so nothing is served that is not
  demanded. A Lift facing a cursor stays until demand reaches it, then
  meets the value it was waiting for and crosses it as ever.
- **Controls cross cursors where they can.** A control at index `i`
  shifts the levels at or above `i`. The region behind a position lies
  at levels no lower than the position's own, its base. Keep that base,
  already raised by the copy's offset, in the cursor's field in place
  of the offset, and recover the offset when it is served, the source
  knowing the position's level. Then a control whose index is at or
  below the base shifts the whole region uniformly. It crosses the
  cursor in one interaction, the base moved by its amount, as a control
  crosses data. A control above the base waits, as in the first form.

The first is the baseline, uniform and demand-driven. The second is an
optimization that keeps controls from waiting, to be weighed by how
often a control meets a cursor on the sharing families and the library.
Its premise, that a region's levels are no lower than its position's,
holds for levels counting enclosing boxes (`lowering-uses-levels`).
That is to be checked against the controls under variables before
relying on it.

**Copies never feed sources.** Serving a cursor reduces only the source,
and no wire runs from a copy into its source, since positive cursors
never interact. So a source's work never consumes a copy's values. The
maintainer (2026-11-11): "I think that needs don't necessarily go only
one way when we start dealing with fixpoints. But, conceptually, we're
never reaching backwards."

The draft's "waits run from copies to sources, never back" was too
strong. A source's pending work may need a cell whose value is, or
holds, a copy of that same source, as a knot or a recursive value
does. That copy's cursors then demand the source at other positions.
Needs run in cycles through cells and fixpoints. No wire reaches
backwards; the waits do. This is why busy state belongs to positions
(`Positions_2026-11-11.md`): a need at another position of a busy
source is a wait, and only the same position on its own chain is a
cycle.

**Marks and several copies.** A control copied by `C1` is marked and
refused by fusion for good, even before `C2` copies it. The mark belongs
to the node, not the copy, which is what `copied-controls-unfused`
needs.

**Scan cost.** A search costs the copy's outstanding cursors. Functions
with many free variables or many arms make long rings. Counting
cursors per copy and search lengths on the sharing families and the
library decides whether dense ids, or another structure, are needed.

## The second reviewer's findings

The second review, kept as written in
[`JoinsFable_2026-11-11.md`](JoinsFable_2026-11-11.md), confirms the
copy's side and finds a gap on the source's side.

**The copy's side holds**, by three facts:
- **monotone:** rewrites relink only their pair's outer peers;
- **disjoint:** a copied node's principal chain is fixed, so subtrees of
  outstanding positions never overlap a copied node;
- **frontier:** every wire between copied and uncopied nodes was given
  a cursor.

It works through the cases:
- the climb to another tree's root: in `\x -> g (h x)`, serving the
  result materializes nothing under it and two joins under the
  variable;
- a copy copied by fans: one ring for both logical copies, as GAL
  shares one body;
- erasure: an erased copy's positive cursor faces the void its variable
  has, which is right.

**Cursors at both ends of one wire are real.** The design never stated
it. In `\x -> (\y -> y) x`, the beta links the two positions directly,
so the serve materializes nothing and joins cursor to cursor: the
maintainer's identity case. It is the materializer's base case.

**The source's side does not yet hold.** "Each port is a separate source
position" and "a position stays valid while the source lives" assume a
finished node keeps its slot, its kind and its ports. Three things in
the kernel break that, none of them fusion:
- **Events renumber ports.** An eraser reaching a finished fan's side
  makes `CopyR` or `MergeR`, the kept side moved from port 2 to port 1
  (`ev.copy`, `ev.merge`, `lin.mv`). In `\x -> k x (h x)` with
  `k a b = b`, a later serve then finds the wrong side's cursor: by luck
  the right value for a copy, the wrong context's for a merge.
- **The sweep frees finished nodes** whose consumers died.
- **Freed slots are reused,** so a cursor at a freed position joins a
  stranger.

The remedy follows `copied-controls-unfused`. In a source, events and
the sweep leave finished nodes alone: the static stays in the link word,
as strategies without events already leave it, and the copy that takes
the node runs the event. This is the one ruling the design cannot do
without.

**The structure lives in the host's heap.** The core sees no erasure and
no collection, so a record it kept for each copy would leak. The second
reviewer weighs three layouts of four-word nodes.
- **A, the draft.**
- **B, packed positions.** A position packed into the header's form and
  field, 26 bits, so that each cursor points to its head: the source and
  offset in one read. The price is a cap of 2^24 nodes on a source,
  reported as an error past it.
- **C, a ring of real wires.** Each cursor has three ports: its own, a
  `prev` and a `next`. The ring is ordinary wiring, which the audit and
  the walk's laws accept. Erasing a cursor is an ordinary rule wiring
  its neighbours together: no dead kind and no lazy unlink.

C is recommended if the cap is accepted, and A otherwise. In A, a dead
cursor is a cursor whose port holds a static, kept findable until
joined. Dense ids would need a contiguous table the heap cannot give,
so they are not for now.

**Other findings:**
- **The transient map costs the source's capacity.**
  `freeze_finished`'s map is an array the size of the source's capacity,
  allocated for each materialization. A scratch array kept per source,
  or a hash, must replace it before anything is measured.
- **Not every negative principal meeting a cursor is a need.** A dead
  operator erases it, as an eraser does.
- **Positive cursors' pairs are waits.** Demand never sees them, but the
  eager strategies and the laws count a stuck pair as an error, so the
  rule table wants a third outcome, "wait", beside rule and stuck.
- **Demand's need test** widens from "table data" to the cursor's kind,
  and `wk.root` and `fw.scan` must stop reading a cursor as a value.
- **Laws:**
  - position stability;
  - monotone finishedness;
  - join sites, by induction on serves;
  - rings collected all or nothing;
  - the cursor kinds' table properties;
  - an oracle: serve then reduce against reduce then copy whole.
- **Tests before any kernel change:** a model over `spike/net.bend` with
  families for each case above, `\x -> k x (h x)` among them, which fails
  today.

**Where the two reviews differ.**
- **Controls.** The second reviewer makes a Lift facing a negative
  cursor a need. That is this review's first form, a cursor served
  wherever demand meets it. Its argument that a control's shift cannot
  be folded holds where the control's index is above the region's base.
  This review's second form folds only below it, so it stands, its
  premise still to check.
- **A host frozen in turn.** The second reviewer adds that positive
  cursors are unfinished for free, since the value facing one is in a
  pair with it.

## Questions for the maintainer

The second reviewer's, merged with this review's:
1. **Position stability.** May finished nodes of a source be exempt from
   events and from the sweep's edits and frees, as copied controls are
   from fusion?
2. **The layout.** Is a cap of 2^24 nodes per source, an error past it,
   acceptable for a ring of real wires? Otherwise the ring is told to
   the collector.
3. **The head node.** May it have no port, or only `prev` and `next`, in
   the rule table and the audit?
4. **A third outcome, "wait",** in the rule table for pairs with a
   positive cursor?
5. **Dead cursors.** Should they stay findable until their position is
   joined?
6. **Stale cursors** at ports the source has since killed, a `FnD`'s
   variable or a fan's dead side: tolerate them, or reconcile them
   during a serve's ring scan?
