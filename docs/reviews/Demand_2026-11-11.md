# Demand — 2026-11-11

A design question raised by the maintainer (2026-11-11): "We'll also need
an eval strategy suitable for copying and fusion. Currently, IIUC, demand
stops when we have a principal port facing the the interface or cursor.
Demand cannot enter a port with a positive principal (ap). Consequently,
demand stops on a bind (lam) and on some control nodes. A viable tweak is
instead to have demand continue following through a lam or control node
(i.e. demand flows through negative aux?) to support partial eval of
function bodies. A related question is how demand should flow through a
fan (merge, IIUC), or what that would even mean. Discuss, contextualize,
advise, perhaps have Fable offer a second opinion."

Two reviewers answer independently: the agent, here, and a Fable
sub-agent, whose opinion is kept as written in
[`DemandFable_2026-11-11.md`](DemandFable_2026-11-11.md). The last
section compares them. This review proposes; the maintainer decides.

## What demand does today

The ports by polarity are listed in `spike/rules.bend`:
- Fn is `[+ fn, - result, + arg]`;
- Ap is `[- ap, - arg, + result]`;
- Copy is `[- input, + left, + right]`;
- Merge is `[+ out, - left, - right]`;
- Lift is `[- in, + out]`, facing the source;
- LiftC is `[+ out, - in]`, facing the consumer.

Every wire joins a positive port to a negative one, and values flow from
positive to negative.

The walk in `spike/kdemand.blend` begins at the interface and follows
principal ports. Each node on its path was entered by an output, a
positive port. From there it follows the node's negative principal to its
peer:
- **The peer is a positive principal:** that is an active pair, and it is
  rewritten.
- **The peer is a positive auxiliary:** that node must reduce first, so
  it is pushed and the walk goes on from it.

So the walk passes only through nodes whose principal is negative: Ap,
Op, Copy, Lift. A positive principal is a value: Fn, Data, Merge, LiftC,
EraP, FnD. The walk stops when the interface faces one, except that a
LiftC there moves past by the root's rule.

**A correction to the question's wording.** Ap's principal is negative,
so demand does enter Ap: through its result, then on to the function it
applies. The nodes with positive principals are the values Fn, Merge
and LiftC. Demand stops at them only at the interface, since inside the
net a positive principal on the walk's path is half of a pair. The
question's point stands, with that correction: demand stops at a value
at the root, and goes no further into a lambda's body.

**Scoping keeps demand going backward** (`net-scoped-arguments`, raised
by the maintainer, 2026-11-11). A function's argument may be used only
within its body: every path from the exposed port to the argument passes
through the function's result. `interaction_net` checks this with a
dominator tree, and glam's lowering never breaks it.

So demand only ever steps backward, from an output to the inputs it
needs. Entering an Ap through its result and going on to the function
is such a step. The one forward step would be entering a Fn by its
argument, and in a scoped net it happens only after copying, where
scoping holds per sharing context rather than by structure. Demand
reports it as state 7.

Three things rest on this. The collector follows inputs only. Body
demand below reaches a function's own variable only from inside its
body. And in a live template's source, pending work reaches the
parameter only through the body, so positive cursors sit only at ports
the result dominates.

## Demand into a value's negative auxiliaries

The proposed tweak continues the walk, past a value reached by its
positive principal, into that value's negative auxiliary ports. Kind by
kind:

| Reached | Its negative auxiliaries | What continuing means |
|---|---|---|
| Fn, FnD | `result`, the body | reduction under the binder |
| LiftC | `in` | looking through a level control to the value behind it |
| Merge | `left`, `right` | each copy context's version of a shared value |
| Data, EraP | none | nothing |

**Through a Fn,** the walk reduces the body toward a head normal form. It
stops at one of three places:
- a value at the body's head;
- the function's own variable, a neutral head (`\x -> x a`): today state
  7, "a variable demanded outside its function's body", which here is
  inside and fine;
- the variable of an enclosing function.

Going on into a neutral head's arguments (an Ap's negative `arg`) would
be full normal form.

**Through a LiftC,** the walk sees a value through a control, as the
root's rule already does at the interface. Inside a body this is
needed: otherwise a value behind a control stops the walk early.

**Through a Merge,** the walk would demand every context's version of a
shared value. A merge's principal facing up is a superposition. The
consumer above faces it with an auxiliary port, and it resolves only
when that consumer's own principal meets something and the merge, facing
it principal to principal, commutes through it. Demanding both sides is
work for contexts that may never demand it: a spark, never demand.
Inside the net, demand reaching a merge from below is always half of a
pair (the commutation), so the question arises only where the walk
starts from an auxiliary port: at the root, where a superposition reads
as none, at a cursor, or under body demand. In each case the merge is a
finished value for the contexts to resolve, and the walk stops there.

**A Copy fan** is already right. Demand reaching it by an output follows
its negative input to the shared value and reduces it once, for both
outputs.

**What body demand costs and risks:**
- **It does not terminate.** A recursive call under the binder is a
  need on a template's leaf. Serving it unfolds the recursion without
  end, as HeapModel says: "Local reduction before freezing reduces
  build-only pairs only, never calls (reducing a call there could unroll
  recursion without end)".
- **It does work no copy may need,** such as both branches of a choice
  under a lambda.
- **It may meet a reflection task,** which early evaluation may not emit.

So body demand is not demand. It is early evaluation: an optimization
that never changes an outcome, stopped by fuel and by reflection tasks
(`early-evaluation-optimization`). `net-demand-whnf` admits it as a
strategy "guaranteed to terminate", the fuel being the guarantee.

## Live templates need positioned demand

A copy's negative cursor names a position in the source: a finished
node's negative auxiliary port, facing a positive auxiliary port of an
unfinished node. Demand at the cursor is today's walk, started there
rather than at the interface. It ends in one of these ways:
- **A value:** a positive principal now faces the position, and that
  structure is materialized into the copy.
- **The frontier:** the walk reaches a finished node's positive
  auxiliary port, such as the function's variable or a fan's output
  under it. That is state 7 reinterpreted as "frontier reached,
  materialize", and positive cursors are joined there.
- **A need:** served in the source, by the same task.
- **Stuck, a cycle, or out of fuel or memory:** as today.

So "demand through a lambda" happens under live templates without any
new rule. Each copy demands a body only when it needs one, through a
cursor, and the source reduces that part once for every copy: lazy
partial evaluation, one position at a time.

## Proposed: three strategies

1. **Demand to weak head normal form at the root,** unchanged
   (`net-demand-whnf`).
2. **Positioned demand,** the same walk started at a cursor. It stops at
   a value, the frontier, a need, stuck, a cycle, or the runtime's
   limits. It is needed by `cells-freeze.cursors`.
3. **Body demand,** a bounded strategy for early evaluation. It walks
   into the negative auxiliaries of Fn, FnD and LiftC, never of Merge.
   It reduces the pairs on its path under fuel, leaves needs unserved by
   default (or serves them within a budget), and stops before a
   reflection task. It runs:
   - on a source before its first copy, to grow the finished part and
     leave fewer cursors (the maintainer's "drive source via demand
     before copying anything at all");
   - when a source is frozen whole;
   - as sparks, later.

**With fusion.** Body demand on a source before any copy fuses freely,
since nothing is marked yet. Positioned demand after copies exist meets
marked controls, which fusion refuses (`copied-controls-unfused`).
Passing through a marked LiftC moves the walk without fusing it.

## Experiments that decide

- **Body demand as a strategy** in `spike/kstrat.bend`, run on the
  library: how many pairs under binders reduce within a fuel of k, 2k
  and 4k a node, and how much of each source becomes finished.
- **On the sharing families:** cursors and joins per copy, with and
  without body demand before the first copy.
- **Needs served under a budget, against left alone,** on recursive
  samples (`hello_recursion.g`, `hello_mutual.g`), to bound the
  unfolding.

## Comparison with the second reviewer

The two agree on the shape: three strategies sharing one walk, differing
in where they start and where they stop.
- **Demand to weak head normal form** stays the semantics.
- **Positioned demand** starts at a cursor.
- **Bounded head demand** is an optimization under
  `early-evaluation-optimization`. It goes through Fn, FnD and LiftC,
  never into a merge's sides or an Ap's argument, so it computes head
  normal form and never full normal form. It leaves needs unserved and
  stops before a reflection task.

Both find that demand never reaches a merge inside a net, because the
consumer's rule distributes over it. Demanding both sides is
speculation, a spark at most.

**What the second reviewer adds:**
- **Controls do not stop demand.** A LiftC at the interface is crossed
  by the root's rule; a Lift on the path is walked through; every pair
  of a control with a base kind has a rule. What looks like a stop at a
  control is the lift the lowering puts under a variable, which the
  walk passes through to the variable, ending in state 7.
- **The common prefix.** Beta links an Ap's result peer to the Fn's
  result peer and its argument peer to the Fn's variable peer
  (`rule.ap KFn`). So the walk to weak head normal form of any demanded
  application, after the beta, is the walk head demand makes from the
  result port, as far as the variable. Head demand under a binder thus
  reduces only pairs that every demanded application of the function
  would reduce. It is wasted only on a function never applied and
  demanded.

  This makes head demand on a function-valued cell's net, when its
  task ends and before its first copy, the natural place to run it.
  There fusion is still free and no mark is set, and it turns per-copy
  work into source work, which is the maintainer's "drive source via
  demand before copying anything at all". In `\x -> (\y -> y) x` the
  pair becomes a wire, and in `\x -> (g c) x`, with `g c` closed, it
  becomes finished structure, with no cursor left.
- **Termination needs one more stop.** `f y = f (g y)` has a weak head
  normal form and no head normal form, so head demand would splice
  `f`'s own template under its binder without end. It stops at a splice
  of the source's own template, or at a splice budget, besides fuel.
- **The frontier is wider than the variable.** After a beta relinks
  peers, a pending node can enter a finished Copy or Lift by its output
  and climb through it to the variable. So positioned demand's frontier
  is "a finished node entered by an output", found by scanning the path
  at the stop, as `fw.scan` already scans for state 7. This corrects
  this review's "the function's variable or a fan's output under it".
- **The scan needs a finished set per source,** not a header bit. A
  bitmap, a word for 32 nodes as the collector's marks are, is built by
  the finished walk and extended at each materialization. Fans and
  functions use a form bit for being unlevelled, and data uses both
  form bits, so only controls have a free bit
  (`copied-controls-unfused` relies on that).
- **A superposition at the interface becomes an outcome of its own,**
  as a void did (`net-void-demanded`), rather than a value with no
  data.

**Where they differ.** This review allowed needs to be served within a
budget; the second reviewer would never serve them in a body pass,
leaving each to become a cursor served under real demand. The second is
simpler and agrees with "serve needs only under real demand"; adopted
as the proposal, with a budget as an experiment at most.

**Experiments,** merging both lists:

2. **The common prefix,** on random terms: head demand, then apply and

3. **Divergent and strict heads** as library entries: `\x -> f (g x)`

4. **A superposition at the root,** sought in the differential store and

5. **Marked controls under head demand** run on a source that already

### Head demand without fuel (the agent's analysis)

Two choices decide what unbounded head demand does: *when* it runs and
*how deep* it goes.

**How deep.** Into nested binders, head demand goes beyond any
application. `\x -> \y -> Ω` applied once and demanded is the value
`\y -> Ω`. Head normal form through both binders diverges. So the pass
must stop at the body's weak head normal form, at a nested Fn, and go no
deeper than an application goes. The common-prefix argument holds
exactly for one binder: after a beta, demanding the application walks
the body to weak head normal form in the same order, as far as the first
place it consults the argument.

**When.** Run eagerly when a function-valued cell's task ends, the pass
diverges on a function that is never applied, such as a handler in a
dict that nobody calls, whose body has no weak head normal form.
Weak head normal form semantics never would. That is the case fuel was
for.

Run instead when the first demanded application reaches the source, the
pass is a prefix of work that application does anyway:
- it walks the same walk, in the same order;
- it stops exactly where the application would first consult its
  argument, which in the source is the frontier;
- if it diverges, the application diverges too.

So it is not early evaluation at all, and no fuel is needed.

**Live templates already do this.** A copy's demand reaches the
negative cursor at the source's body, and positioned demand then
reduces the body in the source to weak head normal form, once for every
copy. The demand-triggered, one-binder head demand is positioned demand
at the body's cursor, nothing more. Nested binders follow lazily, as
copies demand them. The proposal's bounded, eager pass reduces to an
optional extra.

**What follows for the rest, in that form:**
- **Needs** are served, since the application would serve them. Whether
  serving them in the source rather than in the copy pays is the
  measurement the maintainer suggested.
- **Reflection tasks** independent of the argument are emitted when
  first demanded, once for every copy, which `bounded-duplication`
  asks for. A task that depends on the argument stops at the frontier
  and is emitted by each copy, with its own argument.
- **Recursion** without a guard, `f y = f (g y)`, diverges, as the
  program does. A second copy's demand on a source position its own
  task is still reducing would be found as a busy position. Reported as
  a cycle, as a busy cell is, that turns some divergences into errors
  that name their steps. The Rust bootstrap reported cycles so
  (the maintainer, 2026-11-09).
- **Predictability:** each pending pair in a source reduces at most
  once, when a copy first needs it, and never otherwise.

**User control.** Deeper or eager head demand could be asked for by an
annotation on a function, with the user accepting the divergence it
risks. That is "predictably and controlled by user code". Without one,
nothing runs ahead of demand.

### Where the finished bitmap lives

A net is two arrays, its words and its data table, because "each word
of the state costs every step that carries it" (`spike/kprim.bend`,
The state). A third array beside them would cost every interaction, so
the bitmap belongs inside the words array.
- **The flat layout:** a region at the tail of the words, past the node
  capacity, a word for every 32 nodes. It is made when a net first
  becomes a source, and moved when the array doubles, which copies
  everything anyway. The header records whether the region exists.
- **The paged layout** (`spike/kmem_paged.bend`, `store-pages`): a word
  in each page's head for that page's nodes, so a page and its marks
  move together.

The collector's marks today live in a scratch array made for each
collection (`spike/kstrat.bend`, The walk). The finished set must
persist with its source, which is why it cannot be kept that way.

### Merges, sparks and `interaction_net`

**No sparks without an annotation,** as the maintainer leans; recorded
as a leaning.

**Can demand reach a merge in a user's net?** `interaction_net` builds
copies with `.copy N`, and polarity follows from the wiring
(`docs/Design.md`, Interaction Nets): a `.copy 2` whose principal is
wired as an output, to the return port or to a consumer's input, and
whose two auxiliaries are fed by producers, is a merge. So yes, a user
can build one.

Demand never enters a merge's inputs:
- **A consumer's negative principal facing the merge** makes a pair,
  and the rule copies the consumer onto both sides. The merge moves one
  step up, and the walk goes on.
- **At the interface,** there is no rule. Demand ends in state 1 with
  no value.
- **At a cursor or under head demand,** the merge is a finished value
  and is copied.

So in every case demand meets a merge only by its principal. What
remains is what a merge reaching the interface means.

### Superposition, explained

When a fan copies a function, the two copies share one body. Each copy's
argument enters the shared body through a merge, so inside the body the
variable is "the first copy's argument or the second's": a
superposition. Which one is meant depends on which copy is reading,
called the context. Levels track contexts. When the copy fan that made
the merge meets it again, the two fans annihilate and route each
context's value to its own copy (`docs/Design.md`: "copy-copy: join
paired residuals of one duplication process").

So a superposition is a passing state of shared copying, always meant to
be resolved by its partner fan downstream. In a net lowered from lambda
terms, the second reviewer believes no merge reaches the interface
unpaired. One reaching it means "this value is a in one context and b in
another", with no context there to choose. That points to unbalanced
sharing: a hand-built net, or a bug. It is not a result.

Today demand reports it as done, state 1, a value with no data: a
silent answer. The question is whether to report it instead as an
outcome of its own, "a superposition demanded", as `net-void-demanded`
did for a void.

**For context:** HVM treats superpositions as values, and a computation
over them yields a superposition of results, which it uses to enumerate
alternatives (the agent believes so). glam's design has no superposed
value, and its search goes through effects and handlers. A
superposition at the interface is thus an error in glam, unless one day
it is wanted on purpose for search, which would be a design of its own.
The agent recommends an outcome of its own, a diagnostic.

### The second reviewer on head demand without fuel

Its opinion is kept as written in
[`HeadDemandFable_2026-11-11.md`](HeadDemandFable_2026-11-11.md). It
reaches the same answer: drop the fuel and change the trigger.
- **What the pass is.** Head demand runs when a function-valued source
  is first applied with its result demanded. It walks from the Fn's
  result to the body's weak head normal form, through LiftC. It serves
  splices, needs and reflection tasks as the application's own demand
  would, and stops at the variable, at a nested Fn, or at a merge
  facing the position. So defined it is demand at a position, not early
  evaluation, and adds no divergence.
- **What needs an annotation.** Eager or deeper passes need no fuel
  either, but a user's annotation, so that each one names the
  divergence it adds: "zero more cases by default, each annotation
  naming its own".
- **The other stops go with the fuel.** No stop at a splice of the
  source's own template, at needs, or at reflection tasks: each is on
  the prefix of the demanded application.

**What it adds:**
- **Run before the first copy materializes** (its "b′"). The pass runs
  on the source just before the first copy is taken, rather than
  through that copy's cursor. Nothing is marked yet, so fusion is free,
  and every copy, the first included, takes the fused controls and has
  fewer cursors. This refines the agent's "it is positioned demand at
  the body's cursor": same work, ordered before the first
  materialization.
- **A busy state per position.** A cursor position carries the cell
  protocol's states. A position needed on its own chain is a cycle,
  while a busy position on another chain is a wait. This decides the
  cursors review's question of one task per source. Busy state kept per source instead would report a cycle where weak
  head normal form terminates: a body re-entering its own source at
  another position, as a fold's cons case calling itself, or two object
  members calling each other through `self`.
- **Retention.** What a shared prefix builds stays in the source for
  every copy: `\x -> bigList ++ x` keeps `bigList`. This is GHC's
  full-laziness space leak, and it belongs to live templates, not to
  head demand. The remedies are an annotation to opt a function out of
  sharing its prefix, or a collector that frees a source's residue once
  no copy can reach it.
- **Reflection inside a body.** A task independent of the parameter is
  emitted once per function under live templates. Under plain call by
  need it would be emitted once per application, so which is meant is a
  semantic question. The same goes for minting `'scope_unique` atoms.

**Measurements,** in addition to the agent's:
- that head demand then application, against application alone, give
  the same values and counts, as a law of the differential run;
- fusions refused, with and without the pass before materializing;
- peak source size on a family whose prefix builds structure;
- library entries:
  - `f y = f (g y)`, expecting a cycle at a position;
  - `\x -> Ω` forced without application, expecting a value;
  - `\x -> \y -> Ω` applied once, expecting a value;
  - a reflection annotation in a body applied twice, expecting the
    count decided.

**Questions now open,** merged:
1. Is a function ever forced without being applied, by a builtin
   strict in a function or by an annotation? If not, the
   demand-triggered pass and the eager one coincide.
2. Should cursor positions carry a busy state, with a position needed
   on its own chain a cycle?
3. Should a reflection task, or a `'scope_unique` mint, in a body but
   independent of its parameter be emitted once per function or once
   per application?
4. Should needs be served before the first copy, or by its cursor?
   Same outcome; the maintainer suggested measuring.
5. Is an opt-out annotation for sharing a function's prefix wanted now,
   or after measuring retention?
6. Does an annotation for head normal form through all binders, with
   the user owning its divergence, cover the partial evaluation the
   maintainer had in mind?
7. Should a superposition at the interface be an outcome of its own?
   The agent recommends it.

### Retention, explained

A live template keeps its source net for as long as the function lives,
and a top-level function lives for the whole run. Whatever the source
reduces for its copies stays in the source, shared by them all. That is
the point of sharing, but it has a cost in space:

    f x = take x (enumFrom 1 1000000)

The list does not depend on `x`, so under live templates it sits in
`f`'s source. Each application demands it as far as its `take` reads,
and the source keeps every cell any application has read, for as long
as `f` lives. Without sharing, each application would build the list,
read its part and drop it, using time again and again but no lasting
space.

This is the classic trade-off of full laziness: GHC's floating of
expressions out of lambdas shares their work and keeps their results
alive. The remedy discussed was an annotation telling a function not
to share its prefix, so that the expression is built again by each
copy. It is a remedy for space, needed only if measurements show
retention, and the maintainer's `net_arity` idea suits it: an
annotation could choose how many arguments a function takes before
sharing begins.

### Superposition, again, and the maintainer's point

A merge is a fan running backward: two values come in, one comes out.
It arises when a fan copies a function. The two copies share one body,
and inside it the variable is "copy 1's argument or copy 2's", a merge
of the two. Every consumer that meets the merge is copied onto both
sides by the rules, and the merge finally meets the copy fan that made
it. They cancel, and each copy gets its own result. A merge is thus
always in transit toward its partner.

The question was only this: if demand ever finds a merge where it wanted
a value, at `asm.result` or as a `net_arity` result, with no partner to
meet, what should it report? Today it reports done with no data. The
proposal was a clearer error.

The maintainer's point applies. A `Net` value is observed only by
materialization, which copies a merge at its port into the host along

So the question arises only where data is demanded at an interface. It

### Fourth round (2026-11-11): arity and opting out of sharing

The maintainer corrected two readings:

"IIUC, `net_arity` shouldn't impact sharing or retention. That only says
we anticipate a certain usage of a net. My `net_arity` idea was instead
to perhaps let arity guide how far `seq` pushes head-normal form.

If we want to prevent sharing at some fine granularity, IIUC we instead
want an annotation or operation like `const`. Then users could express
`(enumFrom 1 (const 1000000 x))`."

- **Arity guides `seq`, not sharing.** How far `seq` forces a function's
  body could follow its `net_arity`, head normal form through that many
  binders. Sharing and retention are untouched by arity.
- **Opting out of sharing is the user's, by dependence.** Making an
  expression depend on the parameter makes it the work of each
  application, so it is neither shared nor retained.

  The agent adds one point for live templates. A plain `const a b = a`
  would not do it, because the source reduces `const 1000000 x` with
  `x` free, beta and all, to `1000000`, and the expression is shared
  again. So the operation must be one the source never reduces: a copy
  barrier, as the maintainer's `'scope_unique` and `refl:` annotations
  are (third round, item 3). It is reduced only in a copy, where `x` is
  bound, and does not force `x`. One mechanism, barriers marked as
  finished, would then serve the annotations and this operation alike.

The maintainer added (2026-11-11): "I think a general arity annotation
would serve most cases like this, i.e. `anno arity:3 Fn` would wrap a
function to await three arguments before evaluating anything."

The agent's reading, for live templates:
- **Before saturation, nothing is evaluated.** The annotated function's
  source is never reduced. A partial application collects its
  arguments as data, so it is cheap to make and to copy.
- **At saturation, a whole copy.** The third argument splices the
  function's net with all three, a whole copy, so the prefix's work is
  done once for each saturated application, by the user's choice. This
  is the first draft's closures (InsideData, option A) and the
  maintainer's `ApplyK` (2026-11-09), now asked for by annotation rather
  than imposed.
- **The cheap case for effects.** A continuation built at every bind
  could carry such an annotation and cost no source and no cursors.
- **`seq` has nothing to force** before an annotated function is
  saturated, which agrees with letting arity guide how far it goes.
- **Finer than whole functions,** a barrier like `const` would still
  serve a single subexpression; the arity annotation serves most cases.
