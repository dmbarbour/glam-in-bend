# Splice — 2026-11-19

Recommendations, with pros and cons, on three questions the splice's
frame law raises (the Cells plan's `cells-freeze.nested.host.splice`,
[`../plans/Cells_2026-11-09.md`](../plans/Cells_2026-11-09.md)), at the
maintainer's request (2026-11-18): "For the three questions, develop
some recommendations with pros and cons, leveraging advice from Fable."
The law is a frame over an exact list of words
(`serve-write-sets-hybrid`): the splice's three passes,
`S.sp.statics(size, S.sp.links(links, S.sp.nodes(nodes, 0, S.Sp{h,
map}, by)), 0)`, write no word but the list's.

Two reviewers: a Fable sub-agent, whose advice is kept as written in
[`SpliceFable_2026-11-19.md`](SpliceFable_2026-11-19.md) (points `Q1.1`
on), and the agent, here, which checked it against the source and
recommends. This review proposes; the maintainer decides.

## Checked against the source

- The node pass takes every node fresh (`sp.node_at` passes `True{}`,
  `glam/splice.bend:86-89`), so each step is a pop (`P.node`), never a
  `renode`; a pop leaves the taken node's word 1 holding the free list's
  next, writing its header and its payload word alone (`node.fin`,
  `spike/kprim.bend:547`).
- A value's node writes the table's four words first (`P.put`, then
  `tab_put`'s `dt_back`: words 4 to 7), an oversized level the error
  count (`P.err_if`, word 1), each before its pop (`sp.tn`, `sp.fan`).
- The links pass links with `P.link`, which writes both link words
  without a static test (`kprim.bend:385`); a template's ends are always
  node ports, so no static is met.
- The statics pass reads `map[i]` for every `i` below `size`
  (`splice.bend:137-144`), then an eraser's word 1, and writes through
  it (`KN.ld.hd`, `spike/knet.bend:1270-1295`).
- The loader links the root to the interface before its statics pass
  (`knet.bend:1308`); freeze records a port facing the source's
  interface as the template's root and adds no link for it
  (`fz.peer.k`'s `rt` arm, `glam/freeze.bend:296-299`); the materializer
  runs the statics pass before the root is linked (`mz.fz`, then
  `mz.sp`'s crossings and root).

Not rechecked: the second review's effort estimates (days, sizes in
lines) and its account of where the allocator could discharge each
premise (`Q1.5`); both are reasoning from the code.

## S1. A fault to confirm first: an eraser node at the root

From the second review's `Q2.3`, confirmed in the code above. Rules
make eraser nodes (`P.renode(…, P.hd(6, 0), 0)`,
`spike/krules.bend:2393-2421`), and freeze copies one as a template
node (`fz.node.c`'s last arm). An eraser has its principal alone, so an
eraser node at a finished tree's root is the whole tree: a source whose
result is an eraser node. Its template is one node, its root
`T.TE{0, 0}`, no link. In the host, the statics pass finds that eraser,
reads its word 1, which holds the free list's next (say 11), reads the
header at its base (node 8's), and unless that is an eraser writes the
static at word 12 and frees the copy's root, which the root's `leave`
then links. The materializer handles a static at the root by leaving
with the eraser (`R.leave(h, P.era(), nc)`,
`glam/materialize.bend:171`); an eraser node there is the same value and
should take the same path.

Not yet shown reachable: whether a serve stops at a source whose root is
an eraser node. A rule erasing the node that faced the interface makes
one. Recommended: reproduce it in a test, shrink it into the library
(`spike/library.txt`, a fault found), and fix it where the root is read,
so that an eraser node at the root is served as the static eraser is.
Until then, the splice law takes "the root's node is no eraser" in its
template premise (Q2).

## Q1. The fresh nodes

**(a) A premise now, bridged to the allocator later.** The splice
law takes the fresh nodes `ns` as the free list's prefix in the heap's
words (`KMd.chain`), laid out apart (`RG.layout(ns, d)`) and past the
header (`KMd.past_hdr`, needed because `P.put` and `P.err_if` write
header words between pops, which must miss each node's word 1).

- Pros: the law is stated now, over what the program builds; no new
  machinery beyond a chain model and the `node_*` laws applied k times;
  the premise is exactly what the proof consumes (the second review's
  `Q1.1`); the serve's other needs (fresh nodes apart from the ring)
  stay with the composition, not the splice. Runtime cost none.
- Cons: a premise that nothing yet discharges; with Q2's and the
  serve's, the premises pile up, and a pile can be jointly
  unsatisfiable without anyone noticing. A witness answers that: each
  law's witness is an instance where all its premises hold.

**(b) The free list exact over `P.alloc` first.** `FL` proves the free
list exact over a model in Nat, with a free tag per slot that the heap
does not have; over the heap it needs a carried list of free nodes and
of live ones, and a law that every rewrite keeps them (`kernel_free_ok`
is over `KP`'s model, not `P.H`).

- Pros: discharges the premise for real, once.
- Cons: the invariant holds only if every rewrite keeps it, which is
  the heap model's programme, not a step; until then it is a premise
  too, a bigger one, and the splice law waits on it.

**(c) The second review's sharper target (`Q1.5`):** restate
`.host.alloc`'s goal as one prefix law, "the free list's first k nodes
are distinct, laid out apart, past the header, below the capacity, and
none live", which discharges Q1's premise, Q3's premise on the ring,
and `.host.path`'s need that fresh nodes miss the walk's path, together.

**Recommended: (a) now, with (c) named as the allocator's step.**

## Q2. The template's premises

The second review sharpens the set (`Q2.1`), and the agent agrees:
"each port in at most one link" is no frame premise (two links at one
port write a fresh port into it twice; the statics still land inside the
list), so it leaves the frame law, which is then stronger. Missing from
the plan's set: `size` at most the nodes' count (the statics pass reads
`map[i]` for each `i` below `size`; an entry never set is 0, and node 0
is the header). With S1, the premise is a model predicate `TM.ok` over
the template: ends below the nodes' count, ports below 3, each eraser's
principal linked, `size` at most the count, the root's node no eraser.

**(a) A law on what freeze builds.** Freeze is the serve's only
producer of templates.

- Pros: a law, not an audit (the maintainer, 2026-11-18); freeze builds
  the indices and ports by construction, so the law needs no premise on
  the source heap once port uniqueness is out (`Q2.2`); S1 surfaces as
  a clause of it, not a guard.
- Cons: an induction over freeze's emitting walk, its state a record of
  seven fields threaded through a dozen helpers, each wanting a parts
  lemma: the size of `crossings_pend`'s proof. And it covers freeze's
  templates alone; the compiler's reach `S.splice` by another path.

**(b) A check where templates enter.** A pass over the links and nodes,
`O(nodes + links)`, refusing a template that fails.

- Pros: cheap to write; at a module's entry (`book.tk`), negligible at
  runtime; makes the law hold by computation.
- Cons: it is a dynamic check where a law could stand, what the
  maintainer's direction moves away from; at freeze's output it would be
  paid on every materialization.

**(c) A template shape that holds most of them by type** (`Q2.5`): links
stored per node and port, so that no port is out of range or named
twice. Pros: invariants by computation. Cons: it rewrites the template
across lowering, freeze, the loader and the tests; not for this step.

**Recommended: `TM.ok` as the splice law's premise; (a), the law on
freeze, as the step after the splice law; for the compiler's templates,
which do not pass through the serve, a check at `book.tk` marked a
stopgap until `S.splice` gets a law of its own.** Fix S1 first if it is
reachable.

## Q3. The header's words

**(a) A class: the header's words, below `P.iface()`.**

- Pros: one premise, unchanged when growth later writes other header
  words; the shape the serve's premise on the ring wants.
- Cons: it over-approximates by 22 words, so a stray header write in the
  splice (a counter bumped) is not refuted; it would hide that an
  out-of-range link writes words 1 to 3 through node 0; and the ruling
  asks for an exact list.

**(b) The exact words, as a named list** in `spike/kmodel.bend`
(`P.at_errs()` and the table's four, the head beside them), the laws
naming the list, the proofs unfolding it.

- Pros: exact, as the ruling asks; composes by appending; refutes a
  stray write; the representation stays behind a name, as `KMd.lw`
  keeps the link word's (direction 2). Two small laws, `put_keeps` and
  `err_keeps`, in `link_keeps`'s shape, make the node pass's step
  uniform.
- Cons: growth, when it enters, widens the list: a law change, which
  growth makes anyway (it changes the words' depth).

**Recommended: (b) for what the splice writes; the class only as a
premise shape, "every node of L past the header" (`KMd.past_hdr`), in
the serve's composition,** discharged with Q1 by the allocator's prefix
law. `layout` is not widened for it: that would change every law over
`ring.ok` and `pend.ok`.
