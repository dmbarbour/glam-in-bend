# Freeze: what it does, where it sits, and where it goes

and templates (`cells-freeze.nested.host.templates`), at their request
(2026-11-21): "Before the full design review, I want a discussion on
exactly what freeze does, where it would be ideally, what happens or
should happen when a net is fully evaluated, caching and compression

just the review by you and Fable." The agent read the code; a
sub-agent gathered what the docs, records and plans say, checked against
them here. The maintainer's answers follow the account, quoted, and the
steps they set are in the Cells plan. Drafted with the maintainer; the
agenda at the end is for the full review with the second reviewer.

## What freeze does

Freeze reads part of a live net back into a template (`T.Tpl`: nodes,
links, a root, a size), "the inverse of KN.load" (`glam/freeze.bend`,
header): loading what is frozen gives the net frozen. It has three
entries:

| Entry | What it reads back | Used by |
|---|---|---|
| `freeze` (`glam/freeze.bend:392`) | all the interface reaches | `--refreeze` alone (`glam/core.bend`, `refrozen.t`) |
| `freeze_finished` (`:396`) | the finished part, from the interface | tests |
| `freeze_tree(h, v)` (`:410`) | the finished tree at node `v` | every serve (`glam/materialize.bend`, `materialize`) |

Two passes:
1. **A walk**, depth first from the start. Its map of the nodes reached
   is an array the size of the source's capacity
   (`[0 : U32^T.depth_for(31n, cap, 0n)]`, `fz.tree.cap`), made for each
   freeze, a one-node tree too. Finished, it follows auxiliary ports only,
   into nodes whose principal faces back up (`fz.reach.q`); it never
   enters a cursor (`fz.port.c`); it marks a control a copy takes
   (`fz.copied`, `copied-controls-unfused`).
2. **A read-back.** Each node reached becomes a template node, its kind
   and payload: levels, a fan's site and level, a lift's words, a data
   node's value copied out of the source's table (`fz.node.c`). Then
   each port: a static becomes an eraser node, which the splice makes
   static again (`splice-erasers-static`); the interface, the root; a
   node reached, a link written once; anything else, a hole (a cursor
   node) and a crossing, where the wire led (`fz.peer.k`).

**Finished:** a node whose principal faces the interface or an auxiliary
port of a finished node is in no active pair and never can be, so it
never changes; the marks are to keep fusion, eraser events and the
collector off copied ones (`copied-nodes-untouched`), built so far for
controls alone, the rest held by sources running plain demand (the
second reviewer's B3, below).

## Where it runs

The serve, `copy-reduced-function-nets`' batch materialization: a
function-valued cell keeps its net live as a source (`ESrc`,
`glam/core.bend`), each use copying from it as the host's demand reaches
it:

    host demand reaches a use of f
      → its leaf becomes a negative cursor at f's interface, in a ring
      → serve: positioned demand in f's source until a finished tree
        hangs at the position (glam/position.bend)
      → freeze_tree: source heap → template (lists) and crossings
      → splice: template → host heap (node pass, links pass)
      → crossings: each hole joined to a ring cursor at its far end, or
        made a cursor; at the source's root the served cursor leaves
      → later, host demand at one of those cursors serves again

The source's unfinished work reduces there, once for every copy. The
template stands between two heaps: source heap → lists → host heap, the
finished tree walked twice, read then written; data values leave the
source's table and enter the host's. The serve's laws are stated over
the template (`glam/SERVE_LAWS.bend`).

The maintainer had pictured a copy from heap to heap (2026-11-21: "I was
originally envisioning F"). The template between them serves:
- the copy of a source into itself (`self-copies-are-cursors`, `serve1`):
  one heap read and written by one walk, the splice's allocations and
  links changing words the walk has yet to read; the template is a whole
  snapshot before anything is written;
- one copy routine for top-level templates (`ETpl`) and serves alike;
- laws stated over plain data.

Linear arrays are no obstacle in themselves: `materialize` holds the
source and the host at once.

## Findings

**F1. A freeze's map is the size of its source.** `fz.tree.cap` makes an
array of the source's capacity for each freeze. Known: "A scratch array
kept per source, or a hash, must replace it before anything is measured"
(`docs/reviews/Joins_2026-11-11.md`, Other findings); `glam/materialize.bend`'s
"Not yet" note. Verdict: before measuring, as recorded.

**F2. A live source is never released nor frozen again.** In
`glam/core.bend` an `ESrc`'s net is only taken out of the sources and put
back (`SrcOut`); nothing frees it, and a source with nothing left to
reduce stays live and served for the run. The record: "The source stays
live while any copy can reach it by a cursor" (`copy-reduced-function-nets`,
Consequences). Verdict: `cells-freeze.whole`, `cells-freeze.release`.

**F3. Copies at one position freeze the same tree again.** A finished tree
never changes, but each serve at a position walks and reads it back
anew. The second reviewer's cached fragments, "cached in the source, so
the second copy to demand it splices the fragment instead of walking"
(`CursorsFable_2026-11-10.md`, idea 3), survive only as the tentative
`cells-freeze.snapshots`. Verdict: `cells-freeze.fragments`.

**F4. A fully evaluated function stays a live source.** Forcing stops at
weak head normal form (`net-demand-whnf`), so a function's body usually
holds redexes under its binder. Where a net has no active pair and no
vicious circle, every node the interface reaches is finished, so
`freeze_finished` leaves no crossing and holds what `freeze` would, in
another order (A1, below), where the net holds no cursor (B2): the case "a net
freezes only insofar as nothing is left to reduce" allows
(`copy-reduced-function-nets`). Nothing looks for it. Verdict:
`finished-sources-freeze`, `cells-freeze.whole`, `cells-freeze.early`.

**F5. Freeze looks canonical, unproved.** A template's indices follow the
walk, which follows the net's structure and port order, not heap
addresses; so isomorphic nets would freeze alike. A cache keyed by
content needs it (`HeapFable_2026-11-09.md`, A5, unruled). Verdict: a law
when a cache keys on templates (`cells-freeze.format`).

**F6. Text written before freezing was built.** The Cells plan's
re-scoping says "No freezing at run time", its account of the ladder
"Templates load; nothing freezes", and its model `Func{t: Tpl}` "its net
frozen"; `cells-freeze.cells` keeps the net live instead.
`templates-spliced-at-level` says of `copy-reduced-function-nets`'
options "neither is built", then that `cells-freeze.cells` built one.
Verdict: fixed in the commit that records this review, a note at each
(the Cells plan's three; the record's).

## The maintainer's answers (2026-11-21)

The agent put six questions; its options for where freeze sits were
(A) as now, the serve's copy unit; (B) finished trees cached per
position; (C) a wholly finished source frozen once, its heap freed; (D)
early evaluation in the source; (E) freezing at load, under fuel; (F) a
copy heap to heap, no template between.

"I like your options B, C, opportunistic E."

**Q1, the copy mechanism.** "Ideally, shared live nets should move
towards B, C, E. At the moment, we aren't exercising parallelism, but the
more widely a net is shared the higher the interruption overhead per
serve, IIUC. (At the other extreme end of sharing, a linear net could
essentially melt into its only observer to wholly avoid cursors. No need
for work sharing across copies without copies.)"

The agent's reading: a serve's own cost does not grow with the copies
today (a frame's switch, positioned demand's walk, F1's map, a ring's
find for each crossing); wider sharing multiplies serves, and under
parallelism a source, linear, serves one at a time. B makes repeat
serves a lookup and a splice, C ends them, and the melt avoids them: a
whole freeze reads back unfinished pairs too, so a single-use source
moves into its observer by `freeze`, a splice and dropping the source,
the host reducing the rest. It needs to know a source has one use: a
count on the cell, or a linearity fact from lowering.
(`cells-freeze.melt`.)

**Q2, a finished source.** "When a source is wholly finished, its cell
should reduce to an evaluated value, a frozen net template. As for
whether the original is released, that depends on our tactic for
cursors. We could rely on cell-layer GC like we roughly intend for other
partial values, or something more specializes. This will need more
design." (`finished-sources-freeze`; `cells-freeze.whole`,
`cells-freeze.release`.)

**Q3, finished trees cached.** "I like the idea of tree caching per
position, but I'm a bit concerned about space overheads. I think we
should go ahead, with attention to space-time tradeoffs inherent to
caching." (`finished-trees-cached`; `cells-freeze.fragments`.)

**Q4, fully evaluated.** "We can do both early eval and net-layer GC to
find opportunities to freeze nets insofar as it doesn't lead to
divergence or extra reflection tasks. The Rust bootstrap has something
like this." (`early-evaluation-optimization`, revised;
`cells-freeze.early`.)

**Q5, persistent caching.** "We need persistent cache for incremental
assembly, but whether the template is the final version or an
intermediate representation remains open. We might find it more useful
or convenient to develop net canonization and serialization separately.
Especially given that a finished net may still refer (via data table or
cell refs) to unfinished nets." Open (`cells-freeze.format`).

**Q6, the frozen form.** "Not sure what this means or what the
implications are. I sort of imagined a compact frozen net as closer to a
bytecode to efficiently rebuild a net. Efficient representations become
more valuable with caching because we save per serve. We should consider
this carefully."

The agent's account: today's template is Bend lists of node and link
constructors, which the splice interprets in two passes, a node pass
recording each node's address in a map, a links pass looking up both
ends of each link. Three forms:

| Form | Space | Splice per serve | For |
|---|---|---|---|
| lists (now) | large, pointers | two passes, a map | the specification, the laws |
| bytecode | small | a decode per instruction | persistent caching, hashing, storage |
| relocatable image | about four words a node | near a block copy | a hot cache |

A bytecode: a finished part is mostly a tree, each node's principal
facing its parent, so a postfix order gives tree edges for nothing, and
only other links take operands (auxiliary to auxiliary, holes, statics).
An image: the heap's own layout, references relative to its start, a
splice a copy adding the base to each reference not static. Any form
carries references, levels raised at the splice, value table entries
(remapped, or shared as `netdata-borrow` proposes), holes and statics,
and handles to cells, names in a persistent cache, never addresses. The
agent's recommendation: the list template stays the specification; a
compact form proves a decode law (decoded, it is the list template), so
that the serve's laws carry over; bytecode first; canonization and
serialization kept apart.

The maintainer (2026-11-21): "IIUC, a relocatable image would either
need an overhaul to our free list management because we need adjacent
cells. Without that, a well-designed bytecode with a few 'stacks' (e.g.
for aux, data table) can likely catch up on performance." The agent
agrees: the free list hands out nodes wherever they were freed, so an
image needs a contiguous block, a bump region or the allocator's growth,
or a map back again. Bytecode, then, with stacks for what a postfix
order leaves open.

## The full review: the agent's recommendations

Written before the second reviewer's (`FreezeFable_2026-11-21.md`) was
read, so that the two are independent; compared below. Each item names
its step. Facts checked against the tree at `2884596`.

**R1. First, the map the size of the tree (F1;
`cells-freeze.fragments` waits on it).** The walk's map dedupes the nodes
reached and gives a reached peer's template index (`fz.mark`,
`fz.peer.j`). Options:
- a scratch map kept with the source, made once at its size and grown
  with it, cleared after each freeze by walking `seen`: lookups stay one
  array read, a freeze costs its tree; the source's entry carries it;
- the template index written into the source node itself and restored:
  no scratch, but a write to finished nodes, which
  `copied-nodes-untouched` keeps for marks;
- a search over `seen`: no scratch, a lookup the tree's size.

Recommended: the first. It changes no law (the serve's laws take the
template, not the walk).

**R2. A root tree with no crossings is the whole net
(`cells-freeze.whole`, nearly free).** At a source's first serve the
position is the interface, and `freeze_tree` freezes the tree there. If
it yields no crossing, every port of its nodes leads to a static, the
interface or one of its nodes, so it is everything the interface
reaches: the source is wholly finished, and the template is its whole
freeze. The core can then set the cell's value to the template
(`finished-sources-freeze`) with no extra walk. That copy's ring keeps
no cursor once the served one leaves, so nothing else reads the source;
it can be released at once. This covers every function finished at weak
head normal form (the identity, constants, combinators whose bodies are
normal). A source that finishes later, after copies took parts of it,
needs a fresh freeze from the interface, which costs the whole net;
when that runs is open (R6).

**R3. The fragment cache (`cells-freeze.fragments`).**
- *Key and place:* a position of a source, kept with the source, since
  positions mean nothing apart from it and the cache dies with it.
- *Entry:* the frozen tree and its crossings, in the source's terms. A
  crossing's far end is a source port, the same for every copy, and each
  copy joins its own ring, so an entry serves every copy and self-copies
  (`serve1`) alike.
- *Validity:* forever. The tree's nodes are finished and marked
  (`copied-nodes-untouched`). An entry can be smaller than a fresh freeze
  would be now, when parts beyond its frontier have finished since; its
  frontier's cursors are then served later, correct but costing serves.
  Whether to refresh such an entry is a measurement.
- *Hit:* no positioned demand (a tree was finished there before) and no
  freeze walk; only the splice and the crossings.
- *Space:* each entry's size is its template's; a budget per source (its
  live nodes, or a fixed share), least used evicted. The space cost is
  what the maintainer flagged; a compact form (R4) lowers it directly.

**R4. The frozen form: the list template the specification, a bytecode
the form (`cells-freeze.format`).** A sketch, to be designed with the
cache:
- postfix over the tree: a node after the subtrees at its auxiliary
  ports, so that its auxiliary ends are the top of a *port stack* and
  its principal is pushed for its parent: tree edges cost nothing;
- a *wire stack* for the links the tree does not give, auxiliary to
  auxiliary (a lambda's variable): the first end opens a wire, the
  second names it by its distance on the stack;
- a static end and a hole end as operands: no eraser nodes, and a hole
  carries its crossing (source port, polarity, far end);
- payloads in place: levels as frozen (relative to the source, raised at
  the splice), lift words, a data value by index into a *value stack*
  sent once;
- the root, the last node's port.

A splice then runs one pass with two stacks and no map. The decode law,
decoded the bytecode is the list template that freeze would make,
carries the serve's laws over unchanged; a splice straight from the
bytecode needs a second law, equal to the list splice of the decode,
only if decoding shows in measurements. Not recommended: the relocatable
image, which needs contiguous nodes the free list does not give (the
maintainer); a copy from heap to heap, which loses the snapshot a
self-copy needs and the laws' data.

**R5. Statics stay eraser nodes in the list template, for now.** The
template's shape could carry a static end in a link instead
(`SpliceFable_2026-11-19.md`, links by node and port), which would drop
freeze's eraser for a static, the splice's statics handling, the
eraser-root fault class (`docs/reviews/Splice_2026-11-19.md`, S1) and
`SM.made`'s eraser count. But lowering makes templates too, and the
loader's statics pass reads them (`KN.load`). Recommended: the
bytecode carries statics as operands (R4); its decode makes them eraser
nodes, so the list template and every law over it stay as they are.

**R6. Release: a count of rings per source (`cells-freeze.release`).**
A source is read through its rings: each use's ring holds the
situating node that names it (`use.situ`, `glam/core.bend`). A count per
source, up at a use, down when a ring's last cursor is joined or
leaves, is the smallest form of the cell layer's collection the
maintainer named: at zero, with the cell's value a template (R2) or the
cell itself unreachable, the source is freed. The alternative, serving
the cursors left from the whole template, needs the freeze's map from
source positions to template nodes kept with it and a splice of a
template's subtree; possible, more to build, not needed while R2 covers
the common case. Open: whether glam's other partial values use the same
count, which is the cell layer's design, not this step's.

**R7. Early evaluation and the net's collection (`cells-freeze.early`).**
Opportunities, within `early-evaluation-optimization`'s bounds (fuel; a
stop at a need or a reflection, which demand already makes):
- bounded head demand before a source's first copy, which
  `docs/reviews/Demand_2026-11-11.md` recommended: more of the body
  finished, fewer cursors, and R2's case more often;
- reduction in an idle source between serves, later a spark's work.

The net's collection does not change what freeze reaches, which walks
from the interface; it shrinks the source (memory, R1's map) and may be
what makes a source finished where eraser events have cut it off.
Question for the maintainer: which opportunity the net-layer GC was
meant to find.

**R8. The melt at lowering first (`cells-freeze.melt`).** A use is the
only one only if nothing can splice its reference again; at run time a
cell named by a template has as many uses as that template has splices,
which no count at the cell bounds. At lowering it is known: a definition
named once outside any function's body needs no cell and stays linked
in its one net (the Cells plan: "Data definitions stay linked").
Recommended: that first; a melt at run time only with a count the
lowering can prove.

**R9. Canonization and persistent caching.** Freeze is deterministic in
the net's shape: indices follow the walk, which pushes ports in a fixed
order (`fz.ports`); levels are the source's own, a source lowered at
depth 0; values are copied out by value (`P.peek`, the entry kept).
So nets alike in shape from the interface freeze alike: a law to state
once a cache keys on templates, beside the `--refreeze` round trip that
checks `freeze(load(t)) = t` for lowered templates. Agreed with the
maintainer: canonization (what a frozen net is) apart from
serialization (how it is written). A key holds the canonical form's
hash and the versions of the rules and the kernel. A value holding a
handle names a cell relative to the run (the Cells plan: cells "named
relative to it, never with a meaning global to the run"), so a
persistent entry must name what a handle reaches stably, its recipe's
hash, or refuse to cache it.

**R10. Freeze meets the serve's premises by construction
(`cells-freeze.nested.host.splice.freeze`).** As written, `freeze_tree`:
- links node ports `TE{i, p}`, `p` below the kind's arity, at most 3, and
  erasers and holes at `TE{ne, 0}` (`fz.peer.k`, `fz.peer.v`):
  `SM.tpl.ok`;
- sizes the splice's map from the template's size (`T.depth_for(31n,
  size, 0n)`, `glam/materialize.bend`): the nodes no more than its
  slots;
- puts holes at fresh indices from `n`, each with one link, to a node:
  `SV.copy.ok`;
- sets the root only where the interface is met, adding no link there
  (`fz.peer.k`): `SV.root.ok` at the source's root and no link on the
  root's port.

`SV.dyn` follows from `RG.bases`: a base is a multiple of four, a
static has its low two bits ones; a bit lemma, dropped when the
allocator's prefix law is proved. Recommended: prove these after R4
settles the form, so that the law states the form kept.

**Order proposed:** R1, R2 (with the count of R6), R3, R4 with its decode
law, then R7 and R8 as measurements show the need; R9 when persistent
caching starts; R10 with R4.

- *F4* said `freeze_finished` with no cursor "equals `freeze`": it
  holds the same nodes and links, in another order (A1), and only for a
  net holding no cursor (B2). The check, no crossing at the root serve,
  stands.
- *What freeze does* said "the marks keep fusion, eraser events and the
  collector off copied ones": only controls are marked (B3); the rest
  holds because sources run plain demand. `finished-trees-cached` is
  revised to say so.
- *R3* kept a crossing's `far` in the cache "forever": wrong (above).
  The key, too: the tree's root node, which serves the climb's path,
  rather than the served position.
- *R2* set the cell's value to the template: a stale cursor's frame
  wants a live source (`frame.e`, "a cursor's source is no live
  source", `glam/core.bend:1065`), so the entry stays a source holding
  the template, uses splicing it (the second reviewer's section 3).
- *R10* said freeze meets `SV.copy.ok` by construction: not for C1's
  shape.
- *The melt* as "`freeze`, a splice, the source dropped": wrong for a
  source holding a ring (B2). The Cells plan's step is revised to the

**Where they agree:** the list template the specification, a bytecode
the form, a decode law carrying the serve's laws; no relocatable image;
the whole check at the root serve, free; the fragment cache beside the
source, linear with it; rings counted per source as the release's
baseline; early evaluation before a source is filed, bounded, closed
over its net; the melt at lowering; persistent caching with handles
named, not numbered; `SV.dyn` redundant.

**Where they differ, and the agent's view after reading:**
- *Bytecode order.* The agent sketched postfix; the second reviewer
  proposes prefix, an instruction word the node's header, one stack of
  open ports starting with the root's target. Prefix is better: the
  root's target is known first, a subtree is one span, and its B6 (the
  root replaces a ring cursor in every serve, no root placeholder)
  falls out. Prefix.
- *Statics.* The agent kept eraser nodes in the list template and
  statics as operands in the bytecode alone; the second reviewer makes
  a static an end in the list template too, retiring the loader's
  statics pass, which fixes B1's shape and makes freeze alike whichever
  way a net holds its erasers. Both change every law over the template's
  shape; doing it with the format change pays that once. The agent's
  view: statics as ends, with the format change, not before.
- *Cache policy.* The agent proposed a budget with eviction; the second
  reviewer bounds the cache without one: fragments taken where a copy
  first takes nodes never overlap, so they hold the copied part once,
  about a third of its words, and caching at a root's second serve
  spares sources used once. The agent's view: the second reviewer's,
  eviction only if measurement asks; its bound rests on the copies'
  upward closure, a law it asks for before the cache.
- *Cache keys.* The agent keyed a persistent cache on the canonical
  frozen form; the second reviewer keys on the input (the recipe and
  its dependencies' keys), canonical output buying only early cutoff:
  serialization first, canonization later. The second reviewer's is
  right, and is the maintainer's separation.
- *The net's collection.* The agent asked what opportunity it meant;
  the second reviewer reads it as the collector's walk, which meets the
