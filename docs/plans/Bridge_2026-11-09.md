# Bridge: from the ladder to program search and verification

Drafted for the maintainer's review before building (the maintainer,
2026-11-09: "If I said 'go', what would you be doing next? How do we get
there from here?"). The targets are theirs: "Ultimately, direct-style
assembly is just the foundation for assembly programming. If we stopped
there, there'd be no point to such a sophisticated language foundation.
Metaprogramming for program search and verification are the real
targets." This plan sequences work the other plans describe, names the
few steps no plan has, and says where each open design question gets
decided. It designs nothing new: the heap stays with the heap review and
the plans it names ([`../reviews/Heap_2026-11-09.md`](../reviews/Heap_2026-11-09.md),
its F9).

## Where we stand

- **Runs:** the hello ladder through dicts and linked definitions, 21
  samples: texts, lists, locals, lambdas, dicts and tags, names
  ([`HelloLadder_2026-11-09.md`](HelloLadder_2026-11-09.md)).
- **Drafted, not built:** cells ([`Cells_2026-11-09.md`](Cells_2026-11-09.md));
  the heap's options, with the maintainer's answers (the heap review);
  today's records `bounded-duplication` and
  `builtin-imports-compiler-local`.
- **Not built:** recursion, objects, imports, effects, numbers,
  configuration, the capstone, choice, any parallelism.

## How

Features first, single-threaded, along the ladder, as the maintainer
prefers ("push several features and do performance reviews after", the
direction review's Q5). The heap's open questions are decided at one
milestone, `bridge-parallel`, from counters gathered on search
workloads. Until then the only constraint is the heap review's list of
choices costly to reverse: no handle with global meaning inside `Val`,
no page as the unit of ownership, and the protocol's state a task. The
scheduler is de-risked on a side track that never blocks the ladder.

## Milestones

Each is a demonstration: a sample runs, or a number is measured.

1. `bridge-review` — the maintainer reviews this plan.
2. `bridge-recursion` — a recursive definition runs: the Church-boolean
   recursion of the Cells plan's item 6, which the linker refuses
   today. The Cells plan re-scoped as the heap review recommends:
   within one net the static linker already shares definitions, so no
   cells for data-valued definitions as a first rung; a recursive
   function is a template the lowering already produces, spliced where
   demand applies it, at the applying level (the offset the maintainer
   agreed to try); cells, owned by the root heap and named relative to
   it, only for the data a template refers to. A differential run
   against the linker covers every ladder sample.
3. `bridge-objects` — the object samples run, as `ladder-objects`
   lists them: knots as root cells, `self`, `_name`, `extends`, C3 at
   load.
4. `bridge-effects` — the effect samples run, as `ladder-effects` lists
   them, `import 'std` answered by the front end
   (`builtin-imports-compiler-local`). The cost of one effect step is
   measured first, against the Rust bootstrap's "376 K instructions a
   `.r ()` step": search speed is step cost times steps, and eight cores
   buy at most eight times.
   - `bridge-effects.search` — tentative — the first search: `.alt` and
     `.fail` in the list handler, so that `list.head (list.pure p)` is
     backtracking search; a sample that searches, placing queens or
     choosing encodings, sized from the command line at n, 2n and 4n.
     The first point where the targets' shape runs, before the capstone.
5. `bridge-capstone` — the hello ELF: numbers (`ladder-numbers`),
   configuration loaded from `GLAM_CONF` (`docs/CLI.md`), the
   direct-assembly configuration's 758 lines, and `ladder-executable`,
   an ELF that prints.
6. `bridge-macros` — the macro contracts run
   (`samples/contracts/macros/`: a recursive logic DSL, rewrite rules
   whose expansion says "Try layout first, then rewind", a packet
   layout):
   metaprogramming at compile time, macros a feature area of their own
   (`docs/Macros.md`).
7. `bridge-choice` — choice in the direct-assembly handler, its outcome
   "zero or more transactional state results" (the capstone's README),
   and the representative workload, `ladder-measure.workload`.
8. `bridge-parallel` — the decision point. The scheduler over abstract
   tasks (`spike-page-rounds.tasks`) meets real nets: ordered
   alternatives explored ahead of need by priority and cancelled by a
   cut, emissions held until a branch commits, duplication bounded as
   `bounded-duplication` allows. The heap's rulings, handles, ownership
   and partial data in nets, are made here from the counters gathered
   since `bridge-effects`.
9. `bridge-search` — the targets: program search, such as enumerating
   short instruction sequences and testing each against a
   specification; verification, its first task the maintainer's to
   name. Sized families, measured sequential and parallel.

## On "go"

The first week's work:

1. Re-scope the Cells plan as `bridge-recursion` says, recording what
   the maintainer approves.
2. Build recursion: templates spliced at the applying level, the
   Church-boolean sample, the differential run, the level offset as the
   experiment the cells review agreed to.
3. Root cells for the data a template refers to; then objects.
4. Whenever the ladder waits on design: the scheduler over abstract
   tasks, on generated graphs, to learn Bend's balance and round costs
   under fuel quanta.

## Where the open questions are decided

| Question | Milestone | Evidence |
|---|---|---|
| The level offset on a splice | `bridge-recursion` | the differential run; proofs if confidence needs them |
| `need`, `resume` and the splice | `bridge-recursion` | the experiment |
| Laziness inside data made at run time (Cells, item 8) | `bridge-objects`, at its first need | an object capturing a local |
| Partial data as nets or as Bend data | from `bridge-effects` | counters: fans meeting structures |
| Handles global or relative; what is owned | `bridge-parallel` | the need rate and need depth on the search workloads |
| The scheduler's heuristics | `bridge-parallel` | the side track, then the workloads |
| Collection | after `bridge-parallel` | long runs |

## Off this path

Until a milestone needs them, as a proposal: the kernel's tuning
(HeapModel's strategies), Codegen's specialization, the store's pages
and collector (`store-pages`, `store-collection`), NetData's
representation steps, and EvalSpike's remaining spikes other than
`spike-page-rounds.tasks`. Blend keeps its own plans and its utility
(`blend-own-repository`).
