# Blend: the tool, then the kernel

Reviewed by the maintainer, 2026-11-04: looks good, its open questions
answered (below). Blend is our preprocessor of static
objects for Bend (`blend/README.md`; Codegen_2026-11-04.md,
`codegen-vehicle.blend`): `.blend` files in, `.bend` files out, the
objects gone. Its model is set out and its samples are checked
(`codegen-vehicle.blend.samples`). This plan builds the tool, then moves
the kernel's families onto it, measured against the templates they
replace. The samples may change to fit the implementation, keeping their
intention (the maintainer, 2026-11-04).

## What it serves

The kernel's chain from a pair to its rewrite is written once and
compiled once per strategy family through Bend's templates: 51 of
`spike/knet.bend`'s signatures carry its hooks (`~note`, `~fin`, `~wd`,
`~after`, `~erased`) and its types (`~S`, `~R`), as do the 400 generated
rewrites of `spike/krules.bend`; `spike/kstrat.bend` names a family's
hooks at each call into it, and writes a loop per family where a
template cannot recurse. A hook added threads through every signature;
a helper given a second caller splits a segment off every family's
chain. With Blend, a family is an object, its hooks definitions it
gives, its chain its own copy; an affine definition with two callers is
an error before any build. No law imports the kernel's modules
(`spike/LAWS.bend` imports the rule table, the store, the primitives),
so the transition touches none.

## Steps

### The tool

Written in Bend (`generated-sources`), in `blend/blend.bend`, run as
`bend blend.bend COMMAND IN.blend` (a command word: Bend takes
arguments that begin with `-` as its own), the emitted file on its
output, as `spike/tools/gen_krules.bend` writes `spike/krules.bend`.
Built natively once for each version of its sources and of Bend
(`blend/build.sh`, into `results/blend/`; 13 s and 0.4 GB) and run as
`blend/run.sh COMMAND IN.blend`: a run then takes milliseconds, where
`bend blend.bend` checks and compiles the tool each time (1.3 s;
2026-11-04, the maintainer: no need to recheck and rebuild it on every
run). `blend/check.sh` takes 3.7 s with the tool built, 20 s before. Each step ends
with more of the samples passing, the tool's output compared with each
sample's `.bend`, or its error with the `.err`.

1. `blend-read` — built 2026-11-04 — a `.blend` file to a module: its
   bytes read as `spike/load.bend` reads a nets file; lines and
   indentation; the structure line by line (imports, objects and their
   parents, `declare`, members' headers with their sharing, `def` or
   `upd`, name, parameters and result, nested objects, the module's own
   definitions); each body kept as Bend tokens with their lines: names
   with dots, `_`, `^`, `~` before them, numbers with their suffixes,
   strings and chars, comments, the rest as it is. Done when every sample
   reads and its structure prints back.
   - `bend blend.bend read FILE.blend` prints the tree, an item a line
     with its line number, and under each definition the names its body
     holds. A line it cannot read (a header without a name or its
     parenthesis, an object's without `with`, a declaration of no name)
     is kept and printed with `?`, for `blend-objects` to report: reading
     never fails, and a malformed file, an empty one, a CRLF one, tabs,
     bytes past ASCII read without a crash. `blend/check.sh` reads every
     sample, valid and invalid, and fails on a `?` line (the gate, about
     12 s more).
   - Bend has no mutual recursion: each loop that would call a helper
     calling back is one loop over a state record, its step deciding each
     turn, on fuel (the line count, the byte count).
   - Left for later steps: the reader is lenient where Bend will judge
     (a header's stray parenthesis, an object name with a dot, an import
     inside an object); bytes past ASCII print as Latin-1, so
     `blend-emit` writes bytes, not a String.
2. `blend-objects` — built 2026-11-04 — the objects: paths for nested
   objects, parents resolved, C3 as glam linearizes, the definitions each
   concrete object has, `def` and `upd` checked against what it
   inherits, `declare` against what a concrete object defines. Done when
   the samples `upd-undefined`, `def-defined`, `undeclared` and `no-c3`
   fail as their `.err` says, and the rest pass this far.
   - `bend blend.bend objects FILE.blend` prints each object's
     linearization and its definitions, each with the objects that gave
     it, the final first (`BoldLoud`'s `tag`: Bold < Loud < Plain); or
     the errors, `FILE:LINE: message` in line order. `blend/check.sh`
     runs it on every sample: the four print their `.err` exactly, the
     rest no error.
   - A parent's name is found from the object's host outward to the
     module, dotted names by their parts (`Outer.In`); a parent named
     twice is one parent.
   - Errors besides the samples': a parent naming no object, an object
     inheriting from itself, an object defined twice in one scope, a name
     given twice in one object, two parents each introducing a name, an
     import inside an object, a line Blend cannot read; at the top level,
     `upd`, `declare` and sharing marks, the module being no object
     (`blend-module-is-bend`, revised 2026-11-04). Each is reported once:
     an error an object inherits from a parent is the parent's report.
   - Decisions on computed values go through `when`, its arms thunks, as
     Base does: a loop's next turn sits in an arm, inside the loop.
3. `blend-resolve` — built 2026-11-04 — the references in bodies: a
   name called, or passed with `~`, bound to the final definition of the
   innermost object that has it, the longest name defined; `_name` the
   prior, `^name` the host, `Obj.name` that object's; a parameter named
   as a definition an error, then a body's own binders. Done for `shadow`
   and `host-at-module`.
   - `bend blend.bend resolve FILE.blend` makes each concrete object's
     copies, the module's first: its finals, then each prior they reach
     (`BoldLoud.tag` reaches `BoldLoud.tag.Loud`, which reaches
     `BoldLoud.tag.Plain`), and prints what each copy's names reach, by
     the names `blend-emit` will give them. Every valid sample's
     references match its hand-written `.bend`.
   - A bare name is the concrete object's definition, then each host's
     of the object that wrote the body, innermost first, then one of the
     module's definitions, Bend's, its text kept; `^name` the host's
     scope, the module's at the top (`blend-module-is-bend`); a dotted
     name an
     object's definition, the longest object path first, objects found
     from the writer outward; otherwise Bend's.
   - A body's binders are found by line: `case` patterns, lets
     (`x = v`, `(a, b) = v`, `K{x, y} = v`, `a b = ...`), binds and
     annotated lets (`x : A <- m`), lambdas (`x =>`). Their scope is the
     whole body: a local is never named as a definition, so the
     approximation changes no binding, only which collisions it
     reports.
   - Errors besides the samples': a reference to an abstract object's
     definition, a `_name` with no prior, a `^name` its host lacks, a
     local named as a definition. A body copied into several objects
     reports an error once.
   - Stages: each command runs the stages before it and stops at the
     first with errors (read, objects, references).
4. `blend-emit` — built 2026-11-04 — the emitted module: names (`Obj.f`, the
   priors reached `Obj.f.Origin`, copies `Obj.f.c1`), the uses of each,
   the affine check, copies with the affine definitions they alone reach,
   callees first in source order among the unrelated, mutual recursion an
   error, Bend's imports and the module's own definitions as they are;
   what is emitted, every concrete object's definitions or those
   reachable from roots named on the command line, the command line's to
   say (the maintainer, 2026-11-04). Done when every valid sample's
   emission matches its `.bend` and `affine-twice` and `cycle` fail as
   they say; `blend/check.sh` then runs the tool on every sample.
   - `blend/run.sh emit FILE.blend [ROOT...]`: every valid sample's
     emission is its hand-written `.bend` byte for byte, and every
     invalid sample fails with its `.err` exactly; `blend/check.sh`
     holds them to it. Errors go to stderr with the status 1.
   - Order, the tool's choice beyond callees first (the maintainer,
     2026-11-04: Blend leaves it open, as it changes nothing Bend
     observes; so too the copies' numbers): the units in source order
     (the module's definitions and its concrete objects by their lines,
     an object's members in its linearization's order, its own first),
     each emitted after its callees, a walk from each in turn following calls in body order, or
     from the roots named by their emitted names. A cycle is an error
     naming every unit on it.
   - Sharing, over the emitted units, callers first: a copied unit gets a
     copy for each use, its users' copies counted, numbered in the order
     the uses are emitted; an affine unit used once by a multiplied unit
     goes with each of its copies, numbered alike (`Obj.h.c2` called from
     `Obj.g.c2`); an affine unit with two uses is an error naming each
     user and line; a copied unit no unit uses is emitted once by its
     own name. A prior takes its member's sharing.
   - Text: body lines re-indented by the definition's indentation,
     `upd` and the sharing marks gone, tokens as written; the bytes
     decoded as UTF-8 for printing, so text past ASCII passes through.
   - Revised 2026-11-04 (the maintainer): a copied unit is always
     emitted by its own name too, never conditionally
     (`blend-copies-keep-their-name`); the module is no object, its
     definitions Bend's (`blend-module-is-bend`), emitted as written and
     calling a copied unit by its own name. A copied unit used once still
     has its numbered copy, `.c1`, beside the one by its own name.
5. `blend-markers` — built 2026-11-04 — a line before each emitted
   definition naming its source (`# blend: knet.blend:120`), so that
   Bend's errors on emitted code lead back; the samples' `.bend` taken
   up to match.
   - A marker before each definition and none within: a body's lines are
     emitted as they are written, blank ones included, so the line k
     lines below a marker is the source's k lines below the one it
     names. `blend/where.sh FILE.bend LINE` maps a line Bend reports to
     the `.blend` (a type error planted in a sample's body: Bend's line
     15, the source's 12).
6. `blend-generated` — built 2026-11-04 — emitted files checked current
   by `scripts/check_generated.sh`, its lines given the generator's
   arguments (`spike knet.bend ../blend/blend.bend knet.blend`), the
   pre-commit hook with it.
   - A line gives its generator's kind and arguments: `bend` a Bend
     program, `blend` Blend's emission of a `.blend` file, run built
     (`blend/run.sh emit`; the build, 13 s, once for each version of
     Blend's sources). The samples' `.bend` files are generated files
     now, listed there; `blend/check.sh` runs them and the invalid
     samples. The pre-commit hook takes 3.9 s with Blend built.

### What the kernel needs of it

7. `blend-aliases` — contingent on `blend-bend-layer` — a family's
   types: `S`, the state a strategy threads (nothing, a stack), and `R`,
   what a rewrite returns (the net, the net and its stack). An alias
   definition (`alias S = P.Stk`), substituted where named, its sample
   first; or the types left to Bend's `~`, the hooks alone made
   definitions, if aliases prove awkward. An alias is a type specialized
   per family, which the maintainer leaves to Bend until Blend matures
   (2026-11-04, `blend-bend-layer`); so the agent proposes the step's
   other way for the transition: the hooks made definitions, `S` and `R`
   left as Bend's `~` type parameters, two in each signature where the
   chain's now carry seven (51 signatures carry `~S`, 31 `~R`).
8. `blend-generated-objects` — tentative — the generated rewrites as
   members of an object every family inherits, `gen_krules.bend` writing
   a `.blend` where it writes a `.bend`: each family then has its own
   rewrites calling its own hooks, as the templates give it now. Until
   then the families pass their hooks to KR's templates as now.

### The kernel

9. `blend-kernel-chain` — planned — the family chain of knet.bend
   (`interact.f` down to `go.ext.r`, the dispatch, the interpreted
   table's path, `wd`, static erasure, the events) moved to
   `spike/knet.blend`: an abstract object declaring the hooks, a family
   object for each strategy, kstrat.bend calling `Demand.go`,
   `Eager.interact`, and so on, by those names; the interpreted table
   copied with each family, as now. One family first, plain demand,
   measured,
   then the rest. Acceptance: the library's every count and value alike;
   `sharing.py compare` showing each family's chain in segments of its
   own name and none more; the four builds against main within their
   noise or better; no hook left in a signature.
   - `blend-kernel-chain.slice` — tentative — found 2026-11-04: demand's
     `after` is itself a template argument of kstrat.bend's walk
     (`wk.rw(~after, ...)`; plain and collecting demand pass different
     hooks), so a family's `after` can be its own definition only once
     the walk is in the same `.blend`. The first slice, proposed: plain
     demand's walk (`wk.*`) with the chain beneath it in one `.blend`,
     an object for each demand that passes its own `after`; the other
     families on knet.bend's templates meanwhile, the chain in two
     copies until they move.
10. `blend-kernel-loops` — planned — the loops written once per family
    in kstrat.bend (the eager runs with and without events, two stacks,
    the profile, demand's) and knet.bend's per-family drains, each
    written once in the abstract object.
11. `blend-kernel-measure` — planned — the transition's account: build
    time and memory against the templates' (the library's program 51 s
    to 55 s, 3.3 to 4.5 GB), each family's segments and out-of-line
    calls (`sharing.py audit`), lines of hand-written kernel before and
    after.

### Beyond

12. `blend-laws` — tentative — Blend's own laws, in `blend/LAWS.bend`:
    C3's linearization keeps each object's local order and its parents'
    orders; the emitted order puts callees first; an affine definition
    has one use.
13. `blend-partial` — tentative — partial evaluation past a constant
    definition and the C compiler (`blend/README.md`, open questions):
    `static` definitions substituted where used and a `static match`
    pruning arms, then perhaps definitions computed by running Bend when
    generating.
14. `blend-home` — tentative — Blend shared beyond this project: its own
    repository, Bend's hub, its README for readers who know neither glam
    nor the spike.
15. `blend-imports` — tentative — imports between `.blend` files, one
    root module doing a dozen jobs (the maintainer leans to it,
    2026-11-04), rather than several files given as roots, which could
    confuse where they extend one imported object.
16. `blend-macros` — tentative — macros, explicit in the source; Blend
    adds no Bend logic of its own otherwise (`blend-adds-no-bend-logic`).
17. `blend-bend-layer` — tentative — types, laws and proofs overridden or
    specialized per family, revisited once Blend matures (the
    maintainer, 2026-11-04); until then they pass through as Bend.

## Waypoints

The tool's steps in order, each with its samples passing; aliases next,
the one feature the kernel needs that the samples lack; then plain
demand's chain alone, compared with the templates on the library and the
four builds, before any other family moves. A step that finds the model
wrong changes the samples and README first, keeping their intention.

## Revised after the tool emitted

The maintainer, 2026-11-04: the module is no object, to align with
Bend's static top-level modules, while `^name` keeps naming the host's
scope, the module's at the top (`blend-module-is-bend`); a copied
definition is always emitted by its own name, an affine one it alone
reaches copied with it (`blend-copies-keep-their-name`); the order of
emission beyond callees first is the tool's, not Blend's semantics.

## Settled in review

The maintainer, 2026-11-04:

- A plain `.bend` file names an object's definitions by their emitted
  names, `ObjectName.foo`, through an import of the emitted file: no need
  to obscure things.
- Which definitions a module emits, every concrete object's or those
  reachable from given roots, the command line says (`blend-emit`).
- The interpreted table is copied with each family, as the templates
  copy it now, to begin with; whether it becomes one copy shared, taking
  the hooks as Bend's `~`, is decided by performance
  (`blend-kernel-measure`).
