# Blend: the tool, then the kernel

Reviewed by the maintainer, 2026-11-04: looks good, its open questions
answered (below). Blend is our preprocessor of static
objects for Bend (`blend/README.md`; Codegen_2026-11-04.md,
`codegen-vehicle.blend`): `.blend` files in, `.bend` files out, the
objects gone. Its model is set out and its samples are checked
(`codegen-vehicle.blend.samples`). This plan builds the tool, then moves
the kernel's families onto it, measured against the templates they
replace. The samples may change to fit the implementation, keeping their
intention (the maintainer, 2026-11-04).

## What it serves

The kernel's chain from a pair to its rewrite is written once and
compiled once per strategy family through Bend's templates: 51 of
`spike/knet.bend`'s signatures carry its hooks (`~note`, `~fin`, `~wd`,
`~after`, `~erased`) and its types (`~S`, `~R`), as do the 400 generated
rewrites of `spike/krules.bend`; `spike/kstrat.bend` names a family's
hooks at each call into it, and writes a loop per family where a
template cannot recurse. A hook added threads through every signature;
a helper given a second caller splits a segment off every family's
chain. With Blend, a family is an object, its hooks definitions it
gives, its chain its own copy; an affine definition with two callers is
an error before any build. No law imports the kernel's modules
(`spike/LAWS.bend` imports the rule table, the store, the primitives),
so the transition touches none.

## Steps

### The tool

Written in Bend (`generated-sources`), in `blend/blend.bend`, run as
`bend blend.bend COMMAND IN.blend` (a command word: Bend takes
arguments that begin with `-` as its own), the emitted file on its
output, as `spike/tools/gen_krules.bend` writes `spike/krules.bend`. Each step ends
with more of the samples passing, the tool's output compared with each
sample's `.bend`, or its error with the `.err`.

1. `blend-read` — built 2026-11-04 — a `.blend` file to a module: its
   bytes read as `spike/load.bend` reads a nets file; lines and
   indentation; the structure line by line (imports, objects and their
   parents, `declare`, members' headers with their sharing, `def` or
   `upd`, name, parameters and result, nested objects, the module's own
   definitions); each body kept as Bend tokens with their lines: names
   with dots, `_`, `^`, `~` before them, numbers with their suffixes,
   strings and chars, comments, the rest as it is. Done when every sample
   reads and its structure prints back.
   - `bend blend.bend read FILE.blend` prints the tree, an item a line
     with its line number, and under each definition the names its body
     holds. A line it cannot read (a header without a name or its
     parenthesis, an object's without `with`, a declaration of no name)
     is kept and printed with `?`, for `blend-objects` to report: reading
     never fails, and a malformed file, an empty one, a CRLF one, tabs,
     bytes past ASCII read without a crash. `blend/check.sh` reads every
     sample, valid and invalid, and fails on a `?` line (the gate, about
     12 s more).
   - Bend has no mutual recursion: each loop that would call a helper
     calling back is one loop over a state record, its step deciding each
     turn, on fuel (the line count, the byte count).
   - Left for later steps: the reader is lenient where Bend will judge
     (a header's stray parenthesis, an object name with a dot, an import
     inside an object); bytes past ASCII print as Latin-1, so
     `blend-emit` writes bytes, not a String.
2. `blend-objects` — planned — the objects: paths for nested objects,
   parents resolved, C3 as glam linearizes, the definitions each concrete
   object has, `def` and `upd` checked against what it inherits,
   `declare` against what a concrete object defines. Done when the
   samples `upd-undefined`, `def-defined`, `undeclared` and `no-c3` fail
   as their `.err` says, and the rest pass this far.
3. `blend-resolve` — planned — the references in bodies: a name called,
   or passed with `~`, bound to the final definition of the innermost
   object that has it, the longest name defined; `_name` the prior,
   `^name` the host, `Obj.name` that object's; a parameter named as a
   definition an error, then a body's own binders. Done for `shadow` and
   `host-at-module`.
4. `blend-emit` — planned — the emitted module: names (`Obj.f`, the
   priors reached `Obj.f.Origin`, copies `Obj.f.c1`), the uses of each,
   the affine check, copies with the affine definitions they alone reach,
   callees first in source order among the unrelated, mutual recursion an
   error, Bend's imports and the module's own definitions as they are;
   what is emitted, every concrete object's definitions or those
   reachable from roots named on the command line, the command line's to
   say (the maintainer, 2026-11-04). Done when every valid sample's emission matches its `.bend` and
   `affine-twice` and `cycle` fail as they say; `blend/check.sh` then
   runs the tool on every sample.
5. `blend-markers` — planned — a line before each emitted definition
   naming its source (`# blend: knet.blend:120`), so that Bend's errors
   on emitted code lead back; the samples' `.bend` taken up to match.
6. `blend-generated` — planned — emitted files checked current by
   `scripts/check_generated.sh`, its lines given the generator's
   arguments (`spike knet.bend ../blend/blend.bend knet.blend`), the
   pre-commit hook with it.

### What the kernel needs of it

7. `blend-aliases` — planned — a family's types: `S`, the state a
   strategy threads (nothing, a stack), and `R`, what a rewrite returns
   (the net, the net and its stack). An alias definition (`alias S =
   P.Stk`), substituted where named, its sample first; or the types left
   to Bend's `~`, the hooks alone made definitions, if aliases prove
   awkward.
8. `blend-generated-objects` — tentative — the generated rewrites as
   members of an object every family inherits, `gen_krules.bend` writing
   a `.blend` where it writes a `.bend`: each family then has its own
   rewrites calling its own hooks, as the templates give it now. Until
   then the families pass their hooks to KR's templates as now.

### The kernel

9. `blend-kernel-chain` — planned — the family chain of knet.bend
   (`interact.f` down to `go.ext.r`, the dispatch, the interpreted
   table's path, `wd`, static erasure, the events) moved to
   `spike/knet.blend`: an abstract object declaring the hooks, a family
   object for each strategy, kstrat.bend calling `Demand.go`,
   `Eager.interact`, and so on, by those names; the interpreted table
   copied with each family, as now. One family first, plain demand,
   measured,
   then the rest. Acceptance: the library's every count and value alike;
   `sharing.py compare` showing each family's chain in segments of its
   own name and none more; the four builds against main within their
   noise or better; no hook left in a signature.
10. `blend-kernel-loops` — planned — the loops written once per family
    in kstrat.bend (the eager runs with and without events, two stacks,
    the profile, demand's) and knet.bend's per-family drains, each
    written once in the abstract object.
11. `blend-kernel-measure` — planned — the transition's account: build
    time and memory against the templates' (the library's program 51 s
    to 55 s, 3.3 to 4.5 GB), each family's segments and out-of-line
    calls (`sharing.py audit`), lines of hand-written kernel before and
    after.

### Beyond

12. `blend-laws` — tentative — Blend's own laws, in `blend/LAWS.bend`:
    C3's linearization keeps each object's local order and its parents'
    orders; the emitted order puts callees first; an affine definition
    has one use.
13. `blend-partial` — tentative — partial evaluation past a constant
    definition and the C compiler (`blend/README.md`, open questions):
    `static` definitions substituted where used and a `static match`
    pruning arms, then perhaps definitions computed by running Bend when
    generating.
14. `blend-home` — tentative — Blend shared beyond this project: its own
    repository, Bend's hub, its README for readers who know neither glam
    nor the spike.

## Waypoints

The tool's steps in order, each with its samples passing; aliases next,
the one feature the kernel needs that the samples lack; then plain
demand's chain alone, compared with the templates on the library and the
four builds, before any other family moves. A step that finds the model
wrong changes the samples and README first, keeping their intention.

## Settled in review

The maintainer, 2026-11-04:

- A plain `.bend` file names an object's definitions by their emitted
  names, `ObjectName.foo`, through an import of the emitted file: no need
  to obscure things.
- Which definitions a module emits, every concrete object's or those
  reachable from given roots, the command line says (`blend-emit`).
- The interpreted table is copied with each family, as the templates
  copy it now, to begin with; whether it becomes one copy shared, taking
  the hooks as Bend's `~`, is decided by performance
  (`blend-kernel-measure`).
